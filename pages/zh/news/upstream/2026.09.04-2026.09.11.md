本文包括龙架构近一周（截至 UTC+8 时间 2026 年 9 月 11 日 18:00）的龙架构上游社区动向，包括 Linux 内核、编程语言工具链、模拟器及其他项目的移植、优化、平台支持、问题修复和报告等。

本期上游社区动向中的主要亮点有：

- FreeBSD 收到龙架构机器识别号信息，实现上游支持第一步
- MySQL 及 Redis 数据库收到龙架构硬件时钟优化
- Mesa 修复龙架构向量位数上限，有望提高部分驱动性能

## Linux 内核

<!--

线索来源：https://lore.kernel.org/loongarch/

-->

过去一周，Linux 内核的新更动较少，但 Tiezhu Yang 对 `__smp_mb__before_atomic()` 及 `__smp_mb__after_atomic()` 函数实现的讨论和调整值得关注。

### 平台支持

Qunqin Zhao 将龙芯安全引擎 (Loongson Security Engine, SE) 的多节点支持修复补丁[翻新到了](https://lore.kernel.org/loongarch/20260911090256.7834-1-zhaoqunqin@163.com/)第 7 版，相较于数周前的第 5 版，该版修正了中断处理逻辑、DMA 内存大小计算公式等。

### KVM 子系统

Bibo Mao 将先前提交的 `pv_feature` 更新逻辑修复补丁[翻新到了](https://lore.kernel.org/loongarch/20260910022118.2339780-1-maobibo@loongson.cn/)第 2 版。本版重命名了函数并将修改变基 (rebase) 到了最新内核代码上，解决合并冲突。

本周，他还[提交了](https://lore.kernel.org/loongarch/20260909083259.1910290-1-maobibo@loongson.cn/)消息信号中断 (Message Signaled Interrupt) 的注入逻辑优化补丁，取消了部分不必要的参数检查。

### BPF 子系统

上周，Tiezhu Yang [提交了](https://lore.kernel.org/loongarch/20260902005106.22187-1-yangtiezhu@loongson.cn/)一笔针对 `timer_lockup` 测试导致 CPU 软锁死问题的修复。Tiezhu Yang 指出，龙架构是弱内存序架构，而当前实现中松弛的 `atomic_inc()` + `smp_mb__after_atomic()` 组合不足以保证存储和载入操作的顺序执行（后者在当前编译器实现中没有被编译为硬件数据屏障，即 hardware data barrier），与 `bpf_timer_cancel()` 函数文档中明确指出的“须在松弛的 `atomic_inc()` 后跟随完整屏障 (barrier)（原文："Need full barrier after relaxed atomic_inc"）”相悖。

本周，他[提交了](https://lore.kernel.org/loongarch/20260902005106.22187-1-yangtiezhu@loongson.cn/)该补丁集的第二版，将思路改为删除架构特定的 `__smp_mb__before_atomic()` 及 `__smp_mb__after_atomic()` 实现，转为使用基于 `__smp_mb()` 的通用实现。Tiezhu Yang 指出，该实现可正确发出硬件 DBAR 指令，确保存储与载入操作的顺序；他还指出，内核文件系统、驱动、文件管理及网络子系统中有大量调用上述两个函数的地方，均可能存在类似隐患。

此外，他还将 BPF `struct_ops` Trampoline 补丁集[翻新到了](https://lore.kernel.org/loongarch/20260908073506.29734-1-yangtiezhu@loongson.cn/)第三版，继续修缮代码质量。

### 其他代码清理及修复

Karl Mehltretter [订正了](https://lore.kernel.org/loongarch/20260905091743.41006-1-kmehltretter@gmail.com/)关于龙架构 CPU 本地原生比较并交换 (cmpxchg-local) 支持的文档说明；先前该文档仍将龙架构的相关支持情况列为待办 (TODO)，但实际上该支持早在龙架构支持在 5.19 周期进入主线内核时便已存在，而后在 7.0 周期声明支持。

### Binutils

Xi Ruoyao 将指向 GNU indirect function 的 `R_LARCH_GOT_PC_LO12` 在静态链接时解析错误问题的修复补丁更新到第 3 版，Meng Qinggang [合并了](https://sourceware.org/cgit/binutils-gdb/commit/?id=8ec22f3191b1917a06dcbe84f6bbef042462bf5b)该补丁。

Meng Qinggang 为汇编器[提出了](https://sourceware.org/pipermail/binutils/2026-September/151374.html)弃用 `-mignore-start-align` 选项（该选项防止在代码节的开头插入 NOP 指令序列和 `R_LARCH_ALIGN`，但是现在汇编器已经能够自动在它们不必要时将其移除，就不再需要手动指定选项），并修复在显式使用 `.reloc` 编码 `R_LARCH_RELAX` 时未标记对应指令为可能被链接器删除的问题（可能导致链接后出现对齐错误）的补丁。

### LLVM

<!-- lrzlin 审阅；https://github.com/llvm/llvm-project -->

> 本章节由 LLVM 龙架构支持维护者 lrzlin 供稿

hazohelet [报告了](https://github.com/llvm/llvm-project/issues/222088)在使用 clang 构建包含 `_Bitint(24)` 类型的特定 C 代码时，如果使用 `#pragma clang loop vectorize_width(4)` 指定循环向量化宽度会触发崩溃，经过调查是由于 `<4 x i24>` 不属于 Simple 类型，但之前对于 `ISD::SIGN_EXTEND` 做的 Lowering 优化缺失相关判断导致的。Lei Wang [修复了](https://github.com/llvm/llvm-project/pull/222250)该问题，对于非 Simple 类型直接回退到默认路径。

Lei Wang 为内置汇编器[增加了](https://github.com/llvm/llvm-project/pull/222825)部分测试，针对之前[引入的](https://github.com/llvm/llvm-project/pull/211754)在 4/8 字节符号相加或相减时使用 PC-relative 重定位的补丁，补充了 1/2 字节数据重定位的情况。

Wenqiang Wei（ganjue66da）继续[修复了](https://github.com/lat-opensource/lat/pull/464)软浮点模式下 x87 与 SSE 舍入状态相互干扰的问题，在状态加载和信号返回时分别同步；他还[完善了](https://github.com/lat-opensource/lat/pull/425) 16 KiB 宿主页上的客体 4 KiB 权限检查，通过缓存补齐读写、跨页及原子操作检查，防止受保护区域被绕过，17:09 的更新进一步覆盖了 `CMPXCHG8B`。两项均在审查；权限检查需启用 `LATX_MT=1/2`，默认关闭。

yuerengan（y347812075）[提交了](https://github.com/lat-opensource/lat/pull/466)复杂地址计算缓存，复用重复的基址、索引和位移计算；他又基于 Lu Zeng（luzeng87）的工作[添加了](https://github.com/lat-opensource/lat/pull/483)常见指令解码快速路径，以直接解码和模板缓存减少 Capstone 调用。两项均在审查：候选版本默认启用 x86-64 复杂地址缓存及普通翻译解码优化，RIP 相对地址缓存和预缓存默认关闭，通用性能收益仍待验证。

### QEMU

<!-- https://lists.gnu.org/archive/html/qemu-devel/ -->

> 本章节由 QEMU 龙架构支持贡献者 SignKirigami 供稿

Bibo Mao [提交了](https://lists.gnu.org/archive/html/qemu-devel/2026-09/msg01981.html) `CPUTimerState` structure 补丁系列首版，将 `constant_timer_xxx` 函数与 `constant_timer.c` 分别重命名为 `timer_xxx` 和 `timer.c`，并以包含 `QEMUTimer`、IRQ 编号、`CPUState` 与 `CPUSysState` 指针的 `CPUTimerState` 封装 CPU 定时器状态，为后续增加独立 guest 定时器准备结构。

Bibo Mao [提交了](https://lists.gnu.org/archive/html/qemu-devel/2026-09/msg01982.html) MERR CSR 清理补丁，鉴于 KVM 与 TCG 均不支持 MERR 硬件错误处理，从 CPU 初始化、CSR 信息表和反汇编器中移除 `CSR_MERRCTL`、`CSR_MERRINFO1`、`CSR_MERRINFO2`、`CSR_MERRENTRY`、`CSR_MERRERA` 与 `CSR_MERRSAVE`，同时保持 vmstate 不变以维持迁移兼容性。

Xianglai Li [修复了](https://lists.gnu.org/archive/html/qemu-devel/2026-09/msg01984.html) CPU reset 时寄存器残留问题的 V5 版本，通过 `memset()` 清零 `CPULoongArchState` 与 `CPUSysState` 中可重置字段，避免强制重启后残留的 `CSR_ESTAT` 中断状态使虚拟机卡在中断处理流程；相较 V4 恢复 `CPUSysState::end_reset_fields`，防止 `CSR_ASID`、`CSR_PRCFG1`、`CSR_PRCFG2` 和 `CSR_PRCFG3` 被直接清零。

Bibo Mao [提交了](https://lists.gnu.org/archive/html/qemu-devel/2026-09/msg02377.html) LoongArch queue pull request，包含 CPU reset 寄存器清理、DINTC 按物理 CPU ID 二分查找，以及 IPI、PCH PIC 和 EXTIOI 的中断状态显示支持；后者为内核 irqchip 场景补充 `InterruptStatsProvider`，使 `info pic` 可输出同步到用户态的控制器状态以辅助调试。

Bibo Mao [提交了](https://lists.gnu.org/archive/html/qemu-devel/2026-09/msg02950.html) `CPUTimerState` structure 补丁系列 v2，延续定时器函数与文件重命名并为 LVZ 多定时器扩展封装 `QEMUTimer`、IRQ 编号和 `CPUState`；相较首版将 `CPUTimerState` 从 `CPULoongArchState` 移入 `CPUSysState`、移除其中的 `sys_state` 指针，并让 `helper_csrwr_ticlr()` 使用 `timer->irq`。

> 本章节由爱好者社区工作人员供稿

Catty Steve (Catty2014) 向 Khronos 材质处理库 KTX-Software [提交了](https://github.com/KhronosGroup/KTX-Software/pull/1249)龙架构及 RISC-V 构建探测支持，使其可通过构建。KTX-Software 是 Minecraft 使用的 LWJGL 图形库的一部分。

Changqi Hu 向 Redis 数据库[提交了](https://github.com/redis/redis/pull/15769)龙架构硬件时钟支持，在时钟特定测试项目中可实现约 2.8x 耗时优化；他同时向 MySQL [提交了](https://github.com/mysql/mysql-server/pull/749)类似优化。

Cheng Li (shiptux) 向 ROS 项目维护的跨平台 C 语言模拟测试 (Mocking) 库 Mimick [提交了](https://github.com/ros2/Mimick/pull/46)龙架构 (LoongArch64, LP64D) 支持。

SkyBird (skybird233) 向 pnpm 包管理器[提交了](https://github.com/pnpm/pnpm/pull/14683)龙架构二进制发行的构建支持。该包管理 v12 开始使用 Rust 重写，目前无法直接使用 npm 安装。

Haiyong Sun [修复了](https://gitlab.freedesktop.org/mesa/mesa/-/merge_requests/44384) Mesa 错误假设龙架构向量位数上限为 128 位的问题，针对 LASX 将该上限提高到了 256 位。基于 Gallium 设施的 GPU 驱动及 LLVMpipe 性能可能受益。
