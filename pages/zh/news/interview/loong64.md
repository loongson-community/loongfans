关注我们的朋友想必了解，龙架构上游工作积极性虽然高，且经常有喜人的成绩，但也总有一些长期卡点和空缺——从 Chromium 到 Electron，从 PyPI 到 PyTorch，从 Flutter 到 RustDesk…… 一些关键依赖和项目的移植往往因为人力不足难以完成，抑或因为一些非技术原因无法推进。今天我们要介绍的 loong64 社区，便是在成就与艰难并存的上游贡献前的“最后一站”，也是各路用户、开发者和下游用户提前打通应用程序移植、构建和优化的服务站。

> loong64 社区 GitHub 组织：https://github.com/loong64

本期访谈，我们综合了与 loong64 社区核心贡献者吴小白和 Elysia（又称“猫猫侠”）的对话，希望能帮助各位社区好友了解 loong64 社区的诞生背景、当今的主要工作和对未来的计划和期许。

> 编者按：由于采访采用了非同步形式且问答流程未采用录音手段，因此访谈记录是基于现场笔记重新整理的，访谈录的具体内容已由受访者和采访者共同审阅，确定内容准确。

## 您是如何接触龙架构社区的，发起或参与 loong64 的契机又是怎样的？

> 吴小白，社区发起人，是计算机软件行业从业者。

<b>吴小白：</b>loong64 组织的内容最早都是我个人名下的一些个人工作。大概是 2020 到 2021 年间，我在[飞致云 JumpServer](https://www.jumpserver.org/) 负责国产化架构的移植工作，最早也是在这个时候接触的龙芯和龙架构。当时系统的选择上还比较匮乏，基本上只有 Loongnix 20 可用。我最早是因为一部分服务应用无法构建，为了完成工作任务的要求去做了一些零星的移植工作。

<b>吴小白：</b>后来“新世界”这个概念被提出，Debian 也开始做移植了（编者注：大概是 2023 年），所以就开始做一些方便大家用上 Debian 系统的工作了。早期 Debian 还没有安装镜像，我最早做的部分工作是改包补包，让 Debian 比较容易安装上。我也是在这个时候发起的 loong64 项目。

> Elysia，核心贡献者之一，当前是在校大学生。

<b>Elysia:</b> 我是在社区好友的推荐下在 2025 年 5 月份入手了一张龙芯 3A5000 主板，在这之后才比较广泛地去参与龙架构的社区的。最初参与到 loong64 社区中的的契机就是更新了一下社区基于 [crosstool-ng](https://crosstool-ng.github.io/) 维护的交叉编译工具链。在这之后，主要根据自己的软件使用情况和个人的能力，将部分上游有拉取请求（Pull Request 或 PR，部分平台称 Merge Request 或 MR，即“合并请求”）但未被合并的一些补丁重新变基 (rebase) 到较新的版本中，并在使用中对补丁持续维护。

## loong64 社区项目繁多，维护算力是怎样建立起来的？

<b>吴小白：</b>我最早是用公司的服务器做了一部分工作的，后来龙芯官方提供了一些支持。当时龙芯给我们提供了一台 3C5000 服务器，放在我们办公室里，但由于我们自身环境和一些未曾查明的原因，服务器稳定性其实并不是十分好；后来我们经过沟通，就改用了在龙芯那边托管的远程服务器了。但是总地来说，由于网络或者别的各种因素，用于 CI 设施也不是非常靠得住。

<b>吴小白：</b>于是乎，后来我就借用另外一位[社区老哥的思路](https://github.com/lcpu-club/loong64-dockerfiles/issues/3)，拆 Debian 的 QEMU 包，通过模拟运行的方式来运行 CI。这也是我们目前使用的主要构建手段之一，但随着我们慢慢接触到算力、AI 这一部分的应用包，由于代码规模比较大，也就不好继续用模拟器跑了（太慢）；为了解决这个问题，我自购了两台 3A6000 和一台 3B6000 作为维护算力，构建 GCC、MariaDB、Node.js、PyTorch、ONNXRuntime 和 TensorFlow 等这类比较耗时的软件包。

## loong64 社区的定位是上游社区支持和下游应用之间的桥梁吗？

<b>吴小白：</b>也不完全是，比如 [loong64/pypi](https://github.com/loong64/pypi) 项目的本意是作为一个“测试源”存在，将部分移植和验证好的 Python 包提交给 [lpypi](https://lpypi.loongnix.cn/) 等由龙芯维护的软件包/组件仓库。但是后来给对应的仓库提交了一些 PR，发现响应平平，也不太联系得到具体的人（主要是找不到沟通渠道），就慢慢放弃走社区路子了。将 PyPI 的生态也全部从 0 做了一遍，当时想着方便自己，别人想用也可以去用。

<b>编者：</b>您对上游化工作的理解是怎样的？看起来一开始的工作主要也是在业务层面上的，满足需求为主。

<b>吴小白：</b>是的，但是后来慢慢意识到自己维护的成本很高，就想着往上游推送（目前排除 PyPI 包，也有 200+ 个项目了）。这也是一个在中长期控制成本的方法。

## 在您看来，loong64 社区当今的主要工作是什么？

<b>吴小白：</b>有两部分，容器项目 [docker-library](https://github.com/loong64/docker-library) 和 Python 相关的项目。docker-library 是 [Docker Official Images](https://github.com/docker-library) 的龙架构移植，Python 部分目前已经把 wheel 包构建流程走通，可以说 PyPI 上游化的技术条件已经齐备了。

<b>编者：</b>Python 每次编译都有个警告 `WARNING: loongarch64-unknown-linux-gnu is not supported`，跟 PyPI 上游化的事有关吗？

<b>吴小白：</b>编译告警应该是需要 [PEP 11](https://peps.python.org/pep-0011/)（CPython 平台支持，*CPython platform support*）的支持，不影响实际的使用。我目前的工作是准备 [PEP 600](https://peps.python.org/pep-0600/)（针对未来可移植 Linux 构建发行包的 manylinux 平台标签规范，*Future 'manylinux' Platform Tags for Portable Linux Built Distributions*）和 [PEP 656](https://peps.python.org/pep-0656/)（用于基于 Musl 的 Linux 发行包的平台标签规范，*Platform Tag for Linux Distributions Using Musl*）的规范，也与龙芯官方在内的多方技术人员协调了相关规范的制定，如系统基线（目前选用龙蜥，glibc 2.38 及静态 GCC 14）和指令集基线（暂定参照[《龙架构软件开发及构建约定》第 7.3 节](https://github.com/loongson/la-softdev-convention/blob/master/la-softdev-convention.adoc#73-vector-instruction-support)的约定，面向搭载 128 位向量扩展支持的桌面及服务器平台）。最终目标是实现 PyPI 官方发行龙架构 wheel 包，方便开发者使用。

> 编者按：PEP 11 是定义 CPython 平台支持的 Python 改进计划 (Python Enhancement Proposal) 文书，龙架构尚未进入官方第一、二或三级支持的行列。
>
> 另见 Python 官方社区论坛上[关于新增龙架构 PyPI (manylinux) 支持的讨论](https://discuss.python.org/t/path-towards-manylinux-pypi-support-for-loongarch64/105548/2)。

## 在维护 loong64 相关项目过程中遇到过的较为显著的挑战有哪些？

<b>吴小白：</b>没遇到什么问题，因为目前想做的都做成了，苦恼反而集中在“不知道以后做什么”的问题上了，更多的是改善对 AI 相关组件的维护质量，尤其是可复现构建方面。总地来说，龙芯这边支持做得比较好，上游工作都较为到位，我们只是补全了生态位。

<b>Elysia:</b> 在为 [OpenList](https://github.com/OpenListTeam/openlist) 引入龙架构支持的时候遇到了一些小的插曲：当时 OpenList 社区群有龙架构的用户（~~居然真的有人在用~~）提出他们使用的操作系统还是旧世界的发行版，为此我们在构件中专门为旧世界的环境进行了构建。由于旧世界的 Go 编译器和新世界的编译器使用相同的 `GOARCH`, 导致我们在未分离构建缓存目录时，Go 编译器可能会包含异世界的产物，最终导致程序没法运行。

> 编者按：类似的问题也在 GNU/LLVM、Rust 及 CPython/PyPI 等工具链上出现了，指代新旧世界 ABI 的 triple 没有区别。

<b>Elysia:</b> 此外，在我的 3A5000 上部署 Debian 系统也由于旧版固件的限制，需要打了补丁的内核以及 GRUB。针对于此，我在 loong64 组织上维护了一个定制的 Debian LiveCD, 其中就包含了上述的内核以及 GRUB。这个过程中，由于 Debian 中有关制作 LiveCD 的工具 `live-build` 中[有关龙架构支持的补丁](https://salsa.debian.org/live-team/live-build/-/merge_requests/336)尚未合并，在构架时需要自行根据最新的 live-build 仓库应用相关的补丁。

## 对于 loong64 项目的未来，您有什么期许和计划？

<b>吴小白：</b>首先的一个期许是能找到一个能够取代我的核心维护者。虽然短期内问题不大，但以后工作和生活方面的变动可能会导致我的时间不足，影响项目的维护，所以长期来看，可能还是希望能找到有人接手的，可以考虑看看社区里面是否有人有意愿。

<b>编者：</b>志愿驱动的社区项目似乎也经常有这样的烦恼。那么，回到当下，您有什么计划和需要呢？

<b>吴小白：</b>我比较关注后端这一块，主要也是出于兴趣爱好去研究，但这些软件的调试和构建成本都比较高。比如 PyTorch、ONNX Runtime、TensorFlow 这种可以服务算力和 GPU 设备使用需求的 AI 相关组件，使用 QEMU 模拟构建耗时实在过长了，所以有的时候还是要用自购的龙芯设备来手动构建。但是，手动构建无法保证可复现性，进而安全和可交付性方面的矛盾也无法妥善解决——我想做一个可复现的工程，我在我的环境上能过但是不代表其他客户也行。

<b>吴小白：</b>也稍微吐槽下，我自己的 3B6000 台式机，插两条内存有的时候就开不了机，可能有一些兼容性问题吧。

## 后记：社区好友可以做什么

如读者朋友所见，loong64 社区的工作不仅为用户和开发者们提前打通了龙架构移植的工作，也让部分（暂时）无法上游的龙架构支持补丁成为了可持续构建、测试和发布工作的一部分。更重要地，这些工作也为部分上游贡献和标准化工作提供了宝贵的实践经验，也提早辨认了部分问题。

与许多草根开源社区一样，loong64 社区也持续与人力、资源问题“斗争”着。作为 loong64 社区工作的关注者和受益者，我们不仅可以进一步成为贡献者，还可以积极反馈使用问题、支持空缺或提出特性请求，甚至伸出援手，提供如构建机等硬件支持，以及提供协助上游沟通、资料查验等信息支持。
