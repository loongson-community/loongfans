This article outlines LoongArch upstream activities in the past few weeks (up to UTC+8 18:00, October 18th, 2026), including ports, optimization, platform support, bug fixes and reports, etc. in Linux kernel, compiler toolchains, emulators, and other projects.

Highlights in this issue:

- 32-bit LoongArch core design OpenLA132 is now open source
- Container and virtual machine manager Incus merges preliminary LoongArch support
- Compiler Explorer enables Control Flow Graph (CFG) support for LoongArch
- 86Box introduces native LoongArch dynamic recompiler support
- Memtest86+ 9.00 released with enhanced memory information and LASX-powered tests
- Proxmox VE Loong64 Port homepage now online
- LLVM receives patches for cost and schedule model support, enabling performance improvements

During the compilation of this issue, we also interviewed "Mr. Li", author of LoongFire and contact for IPFire upstreaming. How did Mr. Li begin participating in the LoongArch community and what did he discover during the maintenance of LoongFire and IPFire? Read along.

## 32-bit LoongArch CPU Core Design OpenLA132 Now Open Source

Last week, the Loongson Lab published the processor design and verification project for the open-source LoongArch CPU core OpenLA132 in the [GitHub repository loongson/OpenLACores](https://github.com/loongson/OpenLACores). OpenLA132 is licensed under the [Mulan Permissive Software License v2](http://license.coscl.org.cn/MulanPSL2).

![GitHub Repository of the OpenLA132 Kernel](/images/news/upstream/20261018-openlacores-github.png)

According to the [README](https://github.com/loongson/OpenLACores/blob/6403ab5e3a6c8293a48456bcc8a4de5ff8db1930/README.md), the content published this time includes...

> Processor RTL source code, a bare-metal software environment, LoongArch functional-model simulation, Verilator differential verification, and Vivado FPGA implementation flows for the Loongson Laboratory Box and Xilinx VU13P FPGA boards.
>
> It is intended to help users understand and practice chip-design flows including processor RTL design, functional validation, bare-metal program testing, and FPGA boot validation.

OpenLA132 can run on FPGAs such as AMD (Xilinx) XC7A200T and AMD Virtex UltraScale+ XCVU13P.

After the repository was made public, MarsDoge [submitted](https://github.com/loongson/OpenLACores/pull/1) several fixes to the repository for CPUCFG reporting and INVTLB instruction (TLB invalidation) decoding errors based on [LoongArch Reference Manual, Volume 1: Basic Architecture](https://www.loongson.cn/uploads/images/2025032109191292796.%E9%BE%99%E6%9E%B6%E6%9E%84%E5%8F%82%E8%80%83%E6%89%8B%E5%86%8C%E5%8D%B7%E4%B8%80_r1p11.pdf).

## Container and Virtual Machine Manager Incus Merges Preliminary LoongArch Support

![Incus maintainer Benjamin Somers states that LoongArch virtual machine support for Incus has been tested using a Debian Forky image](/images/news/upstream/20261018-incus-loongarch.png)

Back in early September, the Linux container manager LXC (Linux Container) started shipping LoongArch containers to their image server. A month later, Benjamin Somers added LoongArch virtual machine support to the container and virtual machine manager Incus (based on LXC), providing LoongArch hardware users opportunity to manage various applications and services using the tool.

## Compiler Explorer Enables Control Flow Graph Support for LoongArch

Those who study or tinker with compilers are likely familiar with the online interactive compiler - Compiler Explorer. Last week, an upstream maintainer [added](https://github.com/compiler-explorer/compiler-explorer/pull/9256) jump instruction parsing in order to render control flow graphs (CFGs) based on the assembly output from compilers on LoongArch.

![The right panel shows the control flow graph corresponding to the program on the left panel](/images/news/upstream/20261018-compiler-explorer-loongarch-cfg.png)

This feature makes it easier to get a rough sense of a program's control flow, which is helpful for debugging.

## 86Box Introduces Native LoongArch Dynamic Recompiler Support

Two weeks ago, the vintage x86 device emulator 86box merged [LoongArch native dynamic recompiler support by chun-awa](https://github.com/86Box/86Box/pull/8091).

The LoongArch native dynamic recompiler uses the 128-bit vector extension (LSX) to implement all x86 instructions supported by the emulator (including SIMD instructions such as x87 and MMX), allowing to emulate platforms ranging from the oldest 8086/8088 platform up to the highest-end models currently supported by 86Box, such as Slot 1 Pentium II and Socket 370 Celeron (Mendocino) models.

![86Box emulating Windows NT 3.51 on LoongArch and running ["Kunkun 98", a fun AI chat program developed by community friend "Lunzima"](https://github.com/lunzima/llama98-zh)](/images/news/upstream/20261018-86box-on-loongarch.png)

chun-awa is a high school student who has been a long-term 86Box contributor. His contributions include hardware emulation enablements, Chinese localization, and bug fixes. He first came into contact with LoongArch through a Loongson 3A6000 device donated by a community member at Anthon Open Source Community.

While interviewing chun-awa, he stated that while implementing the LoongArch recompiler, he mainly referred to community and official materials such as the [*Unofficial LoongArch Intrinsics Guide*](https://jia.je/unofficial-loongarch-intrinsics-guide/) by Jiajie Chen, [*LoongArch Reference Manual - Volume 1: Basic Architecture*](https://loongson.github.io/LoongArch-Documentation/LoongArch-Vol1-EN.html), and [*Application Binary Interface for the LoongArch™ Architecture*](https://github.com/loongson/la-abi-specs).

Regarding performance expectations, he noted that, due to 86Box's architectural design and requirements for emulation accuracy, the emualtor heavily relies on single-core performance, which is relatively lacking on current LoongArch hardware. However, he also noted that for a domestic Chinese processor powered by a self-developed instruction set architecture, Loongson's performance is commendable.

## Memtest86+ 9.00 Released with Enhanced Memory Information Display and LASX-powered Tests

Several days ago, Sam Demeulemeester (x86fr) released Memtest86+ 9.00, an open-source memory tester, with (intentional and incidental) LoongArch feature improvements.

![Running Memtest86+ 9.00 on a community member's QC622D1_V1.0 motherboard](/images/news/upstream/20261018-memtest86plus-qc622d1-v1.0.jpg)

First, the "intentional" improvement - [added](https://github.com/memtest86plus/memtest86plus/pull/634) LASX-based vector operation tests for LoongArch, to stress memory even more. On the "incidental" side - while adding AArch64 support, Memtest86+ maintainers [added](https://github.com/memtest86plus/memtest86plus/pull/629) DMI-based memory information reading, and detailed memory module information should now be readable on all LoongArch UEFI platforms.

## Proxmox VE Loong64 Port Homepage Now Online

The Proxmox VE Loong64 port has been maintained for nearly half a year, but users have had to go to the GitHub repository to download ISO files, which is somewhat inconvenient.

![The Proxmox VE Loong64 Port homepage](/images/news/upstream/20261018-pve-loong64-home.png)

## libLoL 0.1.12 Released with Support for glibc 2.44 and Fixes for Electron seccomp Sandbox

The LoongArch "Old World (ABI 1.0)" compatibility layer libLoL recently released version 0.1.12, reimplementing the workaround for Old World applications using the seccomp sandbox auditing of fstat, fstatat (such as Electron-based applications), bringing it closer to the current upstream glibc code. Testing showed that the new implementation fixed a crash when launching Lanxin, a Chinese instant messenber for enterprises and organizations.

## Linux Kernel: Progress in Upstreaming CPU Dynamic Voltage and Frequency Scaling and Fixes for 3B6000M Laptops, BPF Optimizations, and Core Code Fixes

This week, the Linux kernel merged or approved two patchsets submitted few months ago, including [fixes for CPU dynamic voltage and frequency scaling for multi-node (and other platforms)](https://lore.kernel.org/loongarch/20260828031201.1500767-1-chenhuacai@loongson.cn/), and [patches for I²C bus clock properties and parsing support](https://lore.kernel.org/loongarch/20260817090721.30582-1-wanghongliang@loongson.cn/). The former, previously was mentioned a few times in previous issues, is the patchset that was required to make use of DVFS with 202605 and 202608 community preview UEFI firmware. For the latter, according to cummunity testing, fixes jittery and irresponsive cursors on touchpads found on some Loongson 3B6000M and 3A6000 laptops.

![The Excelsior NL60R laptop (Loongson 3B6000M) benefits from the aforementioned I²C patchset](/images/news/upstream/20261018-nl60r.webp)

For the BPF subsystem, Tiezhu Yang [added `CPUCFG2_DIV32` feature probing](https://lore.kernel.org/loongarch/20261016081006.26069-1-yangtiezhu@loongson.cn/) for the JIT code in the subsystem to make sure the related code to run normally on the 3A5000 platform without the `DIV32` instruction support. He also [fixed](https://lore.kernel.org/loongarch/20261019013335.13512-1-yangtiezhu@loongson.cn/) stack arguments for indirect trampolines, the `struct_ops_multi_args` test now passes on LoongArch.

In the KVM subsystem, Tao Cui [revised](https://lore.kernel.org/loongarch/20261016095151.1155049-1-cui.tao@linux.dev/) the series of fixes for the virtual irqchip to the 5th revision, continue to fix the code based on feedback from LoongArch KVM subsystem maintainer Bibo Mao.

There are some fixes for the SoC, but mainly from Huacai Chen addressing issues under the 32-bit LoongArch configuration. For the first patch, he [disabled Loongson 2-related modules can be enabled for 32-bit builds](https://lore.kernel.org/loongarch/20261019031436.3523632-1-chenhuacai@loongson.cn/), which, according to the author, "their SoC drviers are not supposed to be used with 32-bit" (although the current Loongson 2 models should be able to run 32-bit kernels, platform support may not be complete). He also sumitted a fix for a [compiler warning](https://lore.kernel.org/loongarch/20261019144240.4035274-1-chenhuacai@loongson.cn/) while building the driver on 32-bit platforms.

Finally, the editor also noticed that Huacai Chen submitted three individual core code fixes to the mailing list - [the first](https://lore.kernel.org/loongarch/20261013062358.60654-1-chenhuacai@loongson.cn/) changed the EIOINTC node ID calculation logic from using the hardcoded `NODE_ADDRSPACE_SHIFT` (44) to using `pa_to_nid()`, [the second](https://lore.kernel.org/loongarch/20261013062858.60822-1-chenhuacai@loongson.cn/) made a similar fix to the PCI and IRQ code, and [the third](https://lore.kernel.org/loongarch/20261013062834.60797-1-chenhuacai@loongson.cn/) disabled the initialization and online operation of empty nodes (without any CPU cores or memory).

All three patches above are cleanups and correctness enhancements to core code (which has been relatively rare lately), but whether they are preparations for new platforms remains to be seen.

## LLVM: Cost Model, Schedule Model Support, and Performance Improvements

Last week, the LoongArch cost model (`TargetTransformInfo`) started landing upstream across several pull requests, which are expected to improve the quality of LLVM auto-vectorization. Yan Tang [submitted support for basic arithmetic instructions](https://github.com/llvm/llvm-project/pull/232230), and Rui Wang [submitted](https://github.com/llvm/llvm-project/pull/233033) cost calculation support for shuffles and element insert/extract operations, achieving a 10% performance improvement in the `nbody` test of `rustc-perf`. The upstream has merged both pull requests.

Lin Runze [submitted](https://github.com/llvm/llvm-project/pull/226064) LoongArch schedule model support, covering all schedulable instructions in LA464/LA664. The models include instruction latency, throughput, misprediction penalty, reorder buffer size, and the number of ALU/AGU/LDQ/STQ entries. Most of the data comes from [Chips and Cheese's microarchitecture analysis of the Loongson 3A6000](https://chipsandcheese.com/p/loongson-3a6000-a-star-among-chinese-cpus/), with the rest from measurements on real hardware.

![Block Diagram of Loongson 3A6000's Microarchitecture (Source: Chips and Cheese)](/images/news/upstream/20261018-chips-and-cheese-3a6000-block-diagram.png)

With the help of the schedule model, MachineScheduler can produce better instruction scheduling sequences. On 3B6000, adding the schedule model improved the score of the SPEC CPU2006 scalar and floating-point test suites by 0.6% and 1.2%, respectively. You can now also use the `llvm-mca` tool to perform static performance analyses on LoongArch instruction sequences! This tool can simulate instruction execution using the instruction latency and microarchitecture information in the schedule model, helping you identify performance bottlenecks.

Lin Runze [submitted initial support for the MachineCombiner pass](https://github.com/llvm/llvm-project/pull/230830), which makes use of instruction latency information from the aforementioned schedule model to reassociate certain associative instructions, shortening dependency chains and improving instruction parallelism. It covers scalar and floating-point add/sub/mul, MIN/MAX, and other operations. Testing showed an approximate 3% performance improvement on the `400.perlbench` subtest of SPEC CPU2006.

## AOSC OS: Core 14, KDE 6 Update, LoongGPU Fixes and Workarounds

Last week, AOSC OS maintainers released the Core 14 core packages update, upgrading GCC to 16.2.0, glibc to 2.44 and re-enabled the previously mistakenly disabled runtime instruction/function implementation probing based on GNU Indirect Function, it is expected to improve performance.

The recent updates to GCC and KDE, however, exposed several latent flaws in the LoongGPU driver. As to the former, the previous code contains an array out-of-bounds access bug. Since it is an undefined behaviour, the bug happened not to cause failures when built with GCC 15, but the driver crashed outright when built with GCC 16. It needs [an extra patch](https://github.com/AOSC-Tracking/loonggpu-kernel-dkms/commit/42e77cbbe9a52b2ef0b15097ff1fdcd951c9b8ee) to fix the bug. For the latter, according to the "Known Issues" section in AOSC's [*KDE 6 Update Notes*](https://aosc.io/news/2026-10-11-kde-6.7-update-notes):

![AOSC OS running Core 14.0.0 and KDE 6](/images/news/upstream/20261018-aosc-os-kde6-on-loongarch.webp)

> If you are using LoongGPU LG110/120 (i.e., the Loongson 7A2000 bridge chip or the 2K2000 integrated GPU), the login screen may fail to display after the update. We preliminarily judge that this issue is caused by a latent flaw in the LoongGPU driver. If you encounter this issue, please use Ctrl-Alt-F3 to switch to a TTY and temporarily switch back to the X11-based SDDM display manager.

AOSC OS maintainer Mingcong Bai later [pushed a workaround](https://github.com/AOSC-Dev/aosc-os-abbs/pull/18073) that disables the Wayland-based Plasma Login Manager on all LoongGPU platforms and falls back to SDDM. This workaround stems from a new issue found on LG200: after starting a KDE 6 X11 session with Plasma Login Manager, the device may fail to enter S3 sleep. Maintainers suspect that the S3 failure was caused by an inability to suspend several GPU processes related to the login manager.

## Debian Fixes OpenJDK 28 and Loongson 2 Kernel Support

In September, a Debian user [reported that they cannot view I²C and PWM information on their Loongson 3A6000 device](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=1148486), and suggest kernel maintainers to enable these functionalities. Debian developer Uwe Kleine-König already [pushed a kernel configuration adjustment](https://salsa.debian.org/kernel-team/linux/-/merge_requests/2101) two weeks ago.

> Editor's note: The `CONFIG_I2C_LS2X` and `CONFIG_PWM_LOONGSON` options enabled this time are also necessary for Loongson laptops, especially for backlight and touchpad support. Backlight support depends on the GPU driver in use, and may require extra patches, see the ["Linux Kernel" section](https://loongfans.cn/en/sdk#kernel) of the Loongson Hobbyists' Community *Developer's Guide* page for details.

In addition, Vladimir Petko recently [fixed the OpenJDK 28 build on LoongArch](https://salsa.debian.org/openjdk-team/openjdk/-/merge_requests/346) and [documented a series of known test errors](https://salsa.debian.org/openjdk-team/openjdk/-/merge_requests/346/diffs#diff-content-ce9b918f10207d4e6ff8c32246fc8ab86e1d9d3e).

## Interview: LoongFire Author and the "Hidden Hand" Behind IPFire's Official LoongArch Support - Mr. Li

While editing this issue of upstream activities, LoongFire author Mr. Li shared a message in his WeChat Moments:

> IPFire now officially supports LoongArch! The LoongFire team has become one of IPFire's official contributors. With the help from Loongfans.cn, the Loongson Hobbyists' Community, and the IPFire community, IPFire has been officially ported to LoongArch. This port is finished based on LoongArch support in GCC, binutils, glibc, the Linux kernel, and other fundamental work done by Loongson/Loongfans open-source communities. IPFire LoongArch port would not have been possible without these work. Because of this port, the LoongFire team is now recognized as one of official IPFire development contributor - a milestone both highlights the substantive work and the long term commitment to the project.

In fact, the official IPFire LoongArch support would not have been possible without Mr. Li's prior communication with Michael Tremer. The LoongFire project also demonstrated, within the open-source community, the adaptability of LoongArch hardware for firewall applications. Therefore, as a preliminary "test run" for our future interview sections, we conducted a brief interview with Mr. Li, hoping to help everyone know more about Mr. Li and other friends who silently dedicate themselves every day to the LoongArch upstream open-source community.

> Editor's note: Following content only represent personal opinions.

### How did you first come into contact with Loongson and the Loongson Hobbyists' Community?

> After I went abroad in 2003, I closely followed computer technology developments. An engineer in the Bay Area who work on CPU related designs often shared online stories about Chinese entrepreneurship in the Bay Area and of about national sentiment - and that included the story of Weiwu Hu and Loongson. So I have heard of Loongson many years ago.
>
> With the deterioration of China-U.S. relations in 2018 and the U.S. goverment's sanctions on Huawei prompted me to do something within my capacity.  I did not know where to start at the beginning, but later I thought of Loongson and bought a 3A5000 desktop computer from AliExpress (but its PSU had some problems and was unusable). Then, and began to follow content shared by Loongson hobbyists. However, at that time, the Loongson community did not seem as mature as it is now.

### What inspired the LoongFire project? What is its relation with IPFire and how do they complement each other?

> I have always wanted to make a self-maintained network-related Linux distribution. I have looked into both OpenWrt and IPFire, but I personally believe IPFire better fits my needs, as it supports enterprise-level network applications such as load balancing. Combined with some personal sentiment, I thought, why not make a network operating system that works with Loongson? This is how LoongFire got started.
>
> LoongFire keeps its functionalities in sync with IPFire, and extends it by adding new capabilities based on eBPF and XDP, in order to complement higher level enterprise-level applications. In the future, as conditions mature, I will also consider commercializing some of LoongFire's features and launching commercial products for enterprise users.

### Why is eBPF important for firewalls and what is the current state of support for LoongArch?

> eBPF is the first technology that I considered as revolutionary in the kernel in many years. eBPF allows to extend based on traditional firewalls, such as XDP network acceleration technology, to meet enterprise-grade applications' demand for high-performance networking.
>
> My philosophy is that, LoongFire should not only serve the Loongson ecosystem, but also be revolutionary. Autonomous and controllable technology does not mean falling behind, it should also mean advanced. Currently I'm using LoongFire myself, but I'm not getting feedback from enterprise applications, so I'm unaware how LoongArch's eBPF support would fare in production environments. We can only find problems and improve them by using it more. Therefore, I hope enterprises and individuals will use it more, so we can find problems and solve them together.

### What is your outlook for LoongArch in firewall hardware? What priorities are worth the community developers' attention now in order to better implement the relevant functionality?

> I'm not particularly familiar with Loongson hardware. I hope Loongson or third-party Loongson hardware design vendors can launch Loongson devices with distinctive features in network hardware optimization. It would be even better if LoongFire could run on these devices. :)
>
> For example, foreign network application vendors have their own in-house network acceleration hardware devices and their own operating systems. I don't yet have a particularly specific feature list, but I think the most important thing right now is for enterprises, communities, and individuals to be willing to actually use it (LoongFire), discover and report problems through use, and then work together to solve them.

### What suggestions and expectations do you have for the related work of the LoongArch community?

> The community is currently able to keep up with the latest Loongson ecosystem technology progress, which is very good. Though I wonder if the community would be interested in setting up a rewards mechanism? For instance, giving symbolic rewards to some community developers who have made contributions in key technologies, and giving recognition at community meetings. This would also help motivate more developers to continue participating.
