This article outlines LoongArch upstream activities in the past week (up to UTC+8 18:00, September 18th, 2026), including ports, optimization, platform support, bug fixes and reports, etc. in Linux kernel, compiler toolchains, emulators, and other projects.

This week's highlights:

- QEMU received the initial patchset to emulate LA664 processors
- The 4th revision of the U-Boot LoongArch support patches has been submitted

This week's activities in the Linux kernel focus on fixes. The patchset previously submitted by Hongliang Wang to add clock related properties to the Loongson 2 series I²C bus driver is likely worth your attention, the patchset is known to fix touchpad input lagging or stuttering issues on some LoongArch laptops, but lacks test feedback.

### Platform Support

Huacai Chen [fixed](https://lore.kernel.org/loongarch/20260916025536.1535237-1-chenhuacai@loongson.cn/) the failure to boot on platforms supporting 256-bit vectors after limiting the SIMD instruction set extension with the `simd=128` parameter, following the Linux 7.0 cycle patch `35ebc4de1059 ("xor: remove macro abuse for XOR implementation registrations")`. The issue was that `cpu_final_simd()`, which sets the vector extension limit, is called by `arch_initcall()`, and this call occurs after `xor_init()` with the LASX implementation, causing the LASX code to fail late during boot. The patch avoids this by using `pure_initcall()`, which is called before `xor_init()`.

Li Jun [submitted](https://lore.kernel.org/loongarch/20260917101050.1002944-1-lijun01@kylinos.cn/) LoongArch PTDUMP (page table dump) functionality to facilitate debugging memory flags and the corresponding potential security issues. Huacai Chen then pointed out that his colleague Haoran Jiang was [iterating](https://lore.kernel.org/loongarch/CAAhV-H4Rgf-k0ys6mDSr_UOz83BsSsZKSFJYgJTrbSH2Jfco1A@mail.gmail.com/) on a patchset for the same functionality, and criticized Li Jun and his colleague for lack of work coordination.

In mid-August, Hongliang Wang submitted the 10th revision of the patch that adds clock properties to the Loongson 2 series I²C bus driver, but he received no feedback since then. This week, he [requested](https://lore.kernel.org/loongarch/db2fdd43-e5bf-3b41-8af5-600151cff899@loongson.cn/) maintainer review for the second time.

Xi Ruoyao reviewed Tiezhu Yang's patch that removes the architecture-specific implementations of `__smp_mb__before_atomic()` and `__smp_mb__after_atomic()`. He believed that the kernel documentation states "for TSO architectures, these two synchronization primitives can be implemented as compiler barriers" and "these two barriers are stronger than acquire/release barriers". On LoongArch, even acquire/release barriers require the dbar instruction, so the previously existing practice of implementing them as compiler barriers should be incorrect. Also, there seems to be no barrier weaker than the full `smp_mb()` (`dbar 0`) on LoongArch that can satisfy the semantics of these two synchronization primitives. Therefore, the patch should be correct.

### KVM Subsystem

## Toolchains

This issue's activities in toolchains focus on routine maintenance and fixes.

### Binutils

(Omitted last week) Alan Modra [reused](https://sourceware.org/git/?p=binutils-gdb.git;a=commit;h=ba3e439f17aabdb5b1a9ca61646f9c22604ab259) logic already provided in architecture-independent code for the virtual input object insertion that the linker (ld) performs during partial linking (`-r`) on LoongArch, to ensure alignment correctness even when mixing inputs with and without relax information.

Meng Qinggang [submitted](https://inbox.sourceware.org/binutils/20260919085650.2568760-1-mengqinggang@loongson.cn/) a patch that, during partial linking (`-r`) on LoongArch, changes the original relocations against section symbols to relocations against normal symbols newly added at the corresponding locations, instead of appending an addend, to fix the perf linking failure found during the ULoong port caused by LoongArch's relax logic not being able to handle relocations with addends. However, Alan Modra believed that the LoongArch relax logic should be improved rather than working around it this way.

### LLVM

Rui Wang [deleted](https://github.com/llvm/llvm-project/pull/223656) the inline assembly part from the previously submitted memory barrier optimization Pass, because these optimizations violated the semantics of inline assembly. He also mentioned that he is writing a [patch](https://github.com/heiher/linux/commits/loong-use-builtins-amo-dbar) that changes all DBAR and atomic instructions in the kernel to use builtins instead of inline assembly.

vincent-163 [submitted](https://github.com/llvm/llvm-project/pull/223921) LoongArch backend lowering support for `STACKMAP` and `PATCHPOINT`, which can be used to implement features such as JIT garbage collection; Weining Lu asked why these two experimental IRs were implemented, and the author explained that he is implementing an X86-LoongArch binary translation project called COGBT, which needs Stackmap to implement accurate exceptions.

### QEMU

<!-- https://lists.gnu.org/archive/html/qemu-devel/ -->

> This section is assembled with contributions from SignKirigami, an active LoongArch contributor to QEMU.

Bibo Mao [submitted](https://www.mail-archive.com/qemu-devel%40nongnu.org/msg1225799.html) a patchset that adds LA664 processor model emulation to QEMU, implementing LoongArch ISA 1.1 features, KVM host capability detection, hardware page table walk (PTW), and DINTC support.

> This section is compiled with contributions from Yao Zi, a LoongArch support maintainer to U-Boot.

- After Tom Rini's patch that makes `CONFIG_OMIT_DTB` prevent device tree building merged, removed the useless empty QEMU device tree

### Issues and Requests for Assistance

> This chapter is compiled with contributions from staff of the Loongson Hobbyists' Community.

yinshiyou [inquired](https://github.com/libjpeg-turbo/libjpeg-turbo/issues/917) the JPEG decoding library libjpeg-turbo about enabling SIMDe (SIMD Everywhere) support by default to allow LoongArch to use SIMD acceleration. The upstream declined, mainly for the following reasons:

1. libjpeg-turbo is the ISO/ITU-T reference implementation of the JPEG decoding library, and hastily introducing SIMDe could raise risks to the standardness of the implementation.
2. The upstream project lacks funding and manpower, and introducing SIMD support for a new architecture could create manpower risks.
3. LoongArch devices are currently not easy to purchase outside China, and subsequent maintenance and testing require multi-generation real hardware support (the previously introduced Loongson MMI and MIPS DSPr2 SIMD support could only be tested incompletely through QEMU due to the lack of hardware).

How to promote official LoongArch SIMD support for libjpeg-turbo remains to be further discussed and awaits the further maturation of international purchase channels.

### Ports, Optimizations, and Fixes

> This chapter is compiled with contributions from staff of the Loongson Hobbyists' Community.

Rabindra Dhakal (QaidVoid) [added](https://github.com/QaidVoid/glycin-ng/pull/25) a LoongArch SECCOMP compatibility flag to glycin-ng, a Glycin-compatible rendering library which he maintains.

huajingyun01 [submitted](https://github.com/nik012003/ripdrag/pull/55) a patch to ripdrag, a terminal file drag-and-drop tool, that updates the `libc` (Rust) dependency, fixing build errors on LoongArch.

Han Li (aooohan) [added](https://github.com/version-fox/vfox-java/pull/62) a Loongnix JDK option to vfox-java, the Java plugin for the multi-language development environment version manager Version Fox, so that LoongArch users can easily use a Java SDK with HotSpot JIT acceleration.

Runze Lin (lrzlin) [submitted](https://github.com/dkaraush/tlottie/pull/15) LoongArch LSX/LASX acceleration support to tlottie, an animation rendering library. The upstream noted that since the LoongArch SIMD intrinsics have not yet reached Rust's stable status, merging may need to be postponed.

Gleb Popov (arrowd) [submitted](https://github.com/ROCm/rocm-systems/pull/11627) another round of LoongArch support patches to ROCm Systems, the AMD GPU compute runtime. The patches are similar to an [earlier pull request](https://github.com/ROCm/rocm-systems/pull/4575) submitted by Xinmudotmoe, but adapt to the test system.
