This article contains LoongArch upstream community activities in the past week (as of July 24th 2026 18:00 CST), including ports, optimization, platform support, bug fixes and reports, etc. in Linux kernel, compiler toolchains, emulators and other projects.

Key upstream community activities:

- Special: PostgreSQL official APT repository now distributes official LoongArch packages
- Special: Project "Donghu", a community-driven Loongson 3B6000 motherboard is now open-source
- Linux kernel received a workaround for the backlight power state loss of 3B6000M laptops when resuming from S3 sleep, and a fix for large module loading
- EDK II received the support for LoongArch ISA V1.1 and hardware PTW (Page Table Walker)
- llama.cpp, a Large Language Model inference framework, received a LASX implementation for the Q4_0_8x8_Q8_0 repack path for Q4_0 quantized models, which can improve the performance by around 7-60%

## Project "Donghu", a Community-Driven Loongson 3B6000 Motherboard is Now Open-Source

![x]()

This week, Loongson Hobbyists Community officially [published](https://github.com/loongson-community/project-donghu) an overview, schematics, datasheets and references for the Loongson 3B6000 motherboard project (Project "Donghu") led by Hengrui Zhang (Harry2005). This is the first open-source motherboard based on the Loongson 3 family of processors.

This project aims to develop a motherboard design that can serve as an alternative to the [Loongson XB612B0_V1.2 motherboard](https://loongfans.cn/en/devices/loongson-xb612b0-v1.2) currently available on the market. Like the existing model, this motherboard is equipped with a Loongson 3B6000 processor but features an enhanced core power supply circuit with the potential to support overclocking. It also comes with 4 DDR4 DIMM slots, providing a more flexible upgrade path.

Most notably, the motherboard distinguishes itself by incorporating the IX7012 PCIe 3.0 bridge from Innosilicon, which has a significantly smaller physical footprint and lower power consumption than the Loongson 7A2000.

All materials of the project are licensed under the [Creative Commons Attribution-ShareAlike 4.0 International](https://creativecommons.org/licenses/by-sa/4.0/) license.

### Key Specifications

- Processor: Loongson 3B6000 (soldered)
- Form Factor: μATX (244×244mm)
- Key design goals
  - Bolstered core power supply - 7+1 phases (MP2975 + MP85956)
  - Alternative bridge chip design based on the low-power InnoSilicon IX7012 bridge chip, with 12 PCIe 4.0 downstream lanes.
  - Four DDR4 DIMM slots with support for Registered ECC modules.
  - Integrated slot for Wi-Fi module - m.2 NGFF + antenna assembly.
  - Southbridge bypass switch for an extra PCIe 4.0 x4 NVMe slot (or PCIe 3.0 x2 as supplied by the southbridge).

### KVM Subsystem

Cui Tao [submitted](https://lore.kernel.org/loongarch/20260722074346.239507-1-cui.tao@linux.dev/) a patch to add support for bulk CSR (Control and Status Register) migration using `KVM_GET/SET_SREGS` macros. This patch has been tested to reduce the time needed for snapshotting one vCPU's core CSR range from about 2ms to about 5μs. The second revision has been submitted to address Bibo Mao's feedback.

### Other Functional and Code Fixes in the Kernel

Haoran Jiang [submitted](https://lore.kernel.org/loongarch/20260722024409.158142-1-haoran.jiang@linux.dev/) a patch to fix oops errors triggered by single-setp debugging after setting breakpoints in the KDB debugger. According to the author's description, this is caused by a mismatch of macros used to analyze problems in `kdb_local()` and `kdb_stub()` (the former uses `KDB_REASON_SSTEP`, and the latter uses `KDB_REASON_OOPS`) on LoongArch. Besides, `ex_vector` should be 0 when determining the reason of a problem, which the current implementation on LoongArch differs from the ones on AArch64 and RISC-V. The patch is pending reviews.

Xuewen Wang [submitted](https://lore.kernel.org/loongarch/20260721025536.1484464-1-wangxuewen@kylinos.cn/) a patch to add a NULL check for `map_bus` in `loongson_gpu_fixup_dma_hang()` function. Huacai Chen then [pointed out](https://lore.kernel.org/loongarch/CAAhV-H4QLa0Y8-MqUPV1cb1oG_kcNRhA06CiN7n_+ekxZVR=ew@mail.gmail.com/) that the patch lacks factual support and is illogical, Xuewen Wang [confirmed](https://lore.kernel.org/loongarch/42e1304d-dc79-400b-b41b-98bc1280a8c9@kylinos.cn/) that the patch is based on subjective assumptions, and gave up on the patch.

Tiezhu Yang [submitted](https://lore.kernel.org/loongarch/20260721090606.8982-1-yangtiezhu@loongson.cn/) a patchset to expand the virtual memory address space for kernel modules from 256MiB to 2GiB, in order to fix the insufficient memory errors when loading some large (e.g. debug symbols unstripped) kernel modules. The second revision has been submitted to address reviewers' feedback.

Tiezhu Yang [submitted](https://lore.kernel.org/loongarch/20260717093907.30010-1-yangtiezhu@loongson.cn/) a patch to replace the custom `cmp_3way()` macro with the generic `cmp_int()` macro that functions the same.

### Binutils

<!-- https://sourceware.org/git/gitweb.cgi?p=binutils-gdb.git -->

Correction: Last week's upstream activities (and the LoongArch Biweekly session on Jul 19) contain a mistake in the description of the fix for `R_LARCH_TLS_DESC64_*` relocations. The fix actually applies to the size of data points modified by these relocations, rather than the size of the relocation entries. The data points modified by these relocations are instructions, which are $4$ bytes long on LoongArch. Setting the size to $8$ caused the linker to read the following instruction after the modified instruction, and write it back as is. This is generally harmless unless that the modified instruction is at the end of a section, then the excessive read and write accesses will be out of bounds. Since BFD linker is single-threaded, and the value read out-of-bounds is written out-of-bounds as is, this behavior usually does not cause any problems. However, if the modified instruction is unfortunately also at end of a memory page, and no subsequent page is mapped, then the out-of-bounds read will trigger a segmentation fault.

Meng Qinggang proposed a patch to change the `DWARF2_USE_FIX_ADVANCE_PC` macro, which the architecture support code provides to the DWARF debug information processing code, to a function-like macro that accepts `FROM` and `TO` parameters. This would allow the architecture support code to determine whether there are any instructions between `FROM` and `TO` that can be removed by linker relaxation, and to inform the debug information processing code to process the relocations in the debug message in place rather than writing them into the target file if no such instruction exists, in order to reduce the size of the target file. This patch is currently open for comments.

### glibc

<!-- https://sourceware.org/git/gitweb.cgi?p=glibc.git](https://sourceware.org/git/gitweb.cgi?p=glibc.git -->

The glibc 2.44 pre-release test result mentioned in the last week's activities contains a failure in `resolv/tst-resolv-res_init-failure`, which currently has been determined to be an architecture-independent issue limited to the test suite (and does not reflect an actual error in the code).

While testing on other architectures, Xi Ruoyao [found](https://sourceware.org/glibc/wiki/Testing/Tests/elf/tst-thp-1) that the test case introduced by the aforementioned change of aligning load segments to huge page boundaries did not fully consider the fact that the page size can differ depending on the kernel configuration on other architectures, causing it to fail on other architectures. According to the feedback from Andreas K. Huettel, the release manager for glibc 2.44, the fix for the issue will be deferred to the 2.45 development cycle.

While testing on other architectures, Yury Khrustalev found that the test case introduced by the aforementioned fix for the exception handling for functions such as `fdiv` on LoongArch did not fully consider the architectures with optional floating-point exception support, causing it to fail with `UNSUPPORTED` on processors that support floating-point exceptions. Yury Khrustalev also [fixed](https://sourceware.org/cgit/glibc/commit/?id=3f3229739ebf6f91ae3f9681f225f0d1ef734163) this issue.

### LLVM

<!-- lrzlin 审阅；https://github.com/llvm/llvm-project -->
Lei Wang [implemented](https://github.com/llvm/llvm-project/pull/210898) `getConstraintRegister` to allow Clang to diagnose inline assembly register clobber conflicts, matching the implementation in GCC.

hev [submitted](https://github.com/llvm/llvm-project/pull/211464) a pull request to allow using `i128` value type with `f` inline assembly constraint when targeting LSX. Although `i128` is not a legal LSX value type, it naturally maps to a single 128-bit LSX vector register in inline assembly. This enables instructions such as `vadd.q` to operate directly on `__int128` operands without requiring explicit vector types.

Taiki Endo [reported](https://github.com/llvm/llvm-project/issues/210431) that the 128-bit `cmpxchg` operation using the `sc.q` instruction may return a corrupted value on CAS failure. Yan Tang suggested that simply replacing `dbar 20` with `dbar 0x700` between `ll.d` and `ld.d` would address the issue, but hev and Taiki Endo pointed out that while using aligned `vld` can ensure the atomicity of the loading operation, `sc.q` is needed on failure to ensure the semantic correctness of CAS operations.

georgejguo [asked](https://github.com/llvm/llvm-project/issues/210052) asked about the issue where the inline assembler emits a paired `R_LARCH_ADD64/SUB64` relocation instead of a single `R_LARCH_64_PCREL` relocation for the undefined symbol `sym - .`, which [affects](https://lore.kernel.org/d89e9c660f06489c59c2f1f7fae0547abbefac71.camel@xry111.site/) objtool's livepatch build.
