This article outlines LoongArch upstream activities in the past few weeks (up to UTC+8 18:00, October 25th, 2026), including ports, optimization, platform support, bug fixes and reports, etc. in Linux kernel, compiler toolchains, emulators, and other projects.

Highlights in this issue:

- LWJGL LoongArch port sees progress in both upstream and downstream communities
- LoongArch cross-compilation toolchain for Windows was released
- Data analytic and machine learning acceleration library oneDAL receives patches for LoongArch support

> Editor's note: We will publish an interview this weekend with the loong64 community core contributors Xiaobai Wu and Elysia, stay tuned!

## Java Game Library LWJGL's LoongArch Port: Progress in Both Upstream and Downstream

Those who have played Minecraft may have heard of the name LWJGL. LWJGL (abbrevation of LightWeight Java Game Library) is a library commonly used by Java games, most well known example of which being Minecraft. Historically, the main obstacle to playing Minecraft on LoongArch had been the lack of LWJGL binaries.

![Running *Minecraft* on LoongArch hardware (Source: OvOla2)](/images/news/upstream/20261025-lwjgl-on-loongarch-loong64.jpg)

As early as 2025, community developer Catty Steve (Catty2014) [had already submitted a LoongArch support patch](https://github.com/LWJGL/lwjgl3/pull/1068) and identified several to-dos in the library's dependencies. Starting this September, some of the dependencies received fixes or support patches that he pushed.Namely the [Base X-platform Library (bx)](https://github.com/bkaradzic/bx) and KhronosGroup's asset processing library and tool [KTX-Software](https://github.com/KhronosGroup/KTX-Software/pull/1249), have both begun accepting LoongArch support patches (the latter currently awaits test devices).

![HMCL is a common way to play Minecraft on LoongArch (Image: Hello Minecraft! Launcher main page)](/images/news/upstream/20261025-hmcl-interface.webp)

The downstream community and applications are also taking actions. For instance, the [HMCL launcher (Hello Minecraft! Launcher)](https://hmcl.huangyuhui.net/) had previously built and implemented the feature to download LoongArch LWJGL binaries along with the game. More recently, loong64 community developers OvOla2 and Xiaobai Wu also [worked together to create a CI release workflow](https://github.com/loong64/lwjgl3/commit/7cf69fa61e734fa1a6d29f3bfab22e9df64928f6), which can build and release LoongArch LWJGL binaries automatically when the upstream updates.

Will LWJGL receive upstream LoongArch support in the future? Let's wait and see.

## The loong64 Community Releases LoongArch Cross-Compiler for Windows

![Building LoongArch binaries on Windows](/images/news/upstream/20261025-loongarch64-cross-on-windows.png)

Elysia-best [implemented a build routine to release LoongArch cross-compiler for Windows](https://github.com/loong64/cross-tools/commit/47103ab157b7a0a349af9930c7d6b8511ea818bb) to cross-tools, a cross-compilation toolchain project maintained by the loong64 community. Developers can now download the toolchain from the [GitHub repository](https://github.com/loong64/cross-tools/releases/tag/20261022).

## The Data Analytic and Machine Learning Acceleration Library oneDAL Receives a LoongArch Support Patch

Last week, Gleb Popov [submitted initial LoongArch support](https://github.com/uxlfoundation/oneDAL/pull/3902) to the oneAPI Data Analysis Library (oneDAL) maintained by the UXL Foundation, enabling the library to build on LoongArch. The patch is currently under review by the project maintainers. The UXL Foundation is a cross-vendor, cross-architecture accelerator programming framework initiated by Intel.

Currently, the project maintainers are requesting LoongArch devices to support their CI testing. Staff of the Loongson Hobbyists' Community staff are currently in contact to discuss the matter.

## ELF Utilities (elfutils) Receives LoongArch eu-stackprof Profiler Support

Recently, the ELF toolset elfutils released version 0.196, which introduced `eu-stackprof`, a stack-based profiling tool that interfaces with the Linux kernel's `perf_event` mechanism. `eu-stackprof` can sample at system level or for a specific process tree. Community developer Xuerui Wang subsequently [submitted a patch to port `eu-stackprof` to LoongArch](https://sourceware.org/pipermail/elfutils-devel/2026q4/009792.html) and, hopefully very soon, you will be able to use this new tool to profile LoongArch binaries.

## GNU Toolchain: This Week's Maintenance Report

This week's activities on the GNU toolchain mainly consists of routine fixes.

### GNU Compiler Collection (GCC)

Recently, GCC received an architecture-independent optimization: when it is known that the two inputs of a bitwise `OR` operation have no common bits set to 1, it replaces the bitwise OR with an addition. This helps make use of instructions such as LoongArch's `alsl` or x86's `lea`. But unfortunately, the LoongArch backend optimizations that use `bstrins` and `bytepick` instructions stopped matching the intermediate code produced after the bitwise OR was replaced with an addition, causing them to stop working. Xi Ruoyao [submitted a fix for the above optimizations](https://gcc.gnu.org/pipermail/gcc-patches/2026-October/735788.html).

### GNU C Library

Deng Jianbo [submitted a patch to the `sysconf` function on LoongArch that allows to obtain cache-related information via the `cpucfg` instruction](https://sourceware.org/pipermail/libc-alpha/2026-October/181328.html). This feature is can help applications obtain cache information through architecture-independent APIs, thereby reducing the effort required for porting.

Adhemerval Zanella [submitted a patch that adds `__BEGIN_DECLS`/`__END_DECLS` macros to the `fpu_control.h` on LoongArch](https://sourceware.org/pipermail/libc-alpha/2026-October/181411.html) to fix the issue where `__loongarch_fpu_setcw` and `__loongarch_fpu_getcw` are incorrectly mangled when called from C++ code. This was found during a comprehensive audit for missing `__BEGIN_DECLS`/`__END_DECLS` issues, and no actually affected downstream projects were found (in any case, it is better to use the portable `fegetenv`/`fesetenv` functions rather than architecture-specific ones when writing code).

### Binutils

Zhao Zhou [removed the assembler's (GNU as) "support" for the non-existent `xvhseli.d` instruction](https://sourceware.org/cgit/binutils-gdb/commit/?id=214080ae5328425c3395a116e45d3e4c26f29515), though the editorial team is not entirely sure why logic for assembling a non-existent instruction existed in the first place. In addition, he [submitted a patch](https://inbox.sourceware.org/binutils/20261021015156.65492-1-zhaozhou@loongson.cn/) to prevent the assembler (as) logic for handling out-of-range conditional branch instructions (for example, rewriting `beq a0, a1, foo` as `bne a0, a1, 4; b foo`) from incorrectly applying to `jirl` instructions carrying `R_LARCH_B16` relocations - such `jirl` instructions are unlikely to exist in real code.
