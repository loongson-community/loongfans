This article contains LoongArch upstream community activities in the past week (as of September 4th 2026 18:00 CST), including ports, optimization, platform support, bug fixes and reports, etc. in Linux kernel, compiler toolchains, emulators and other projects.

Key highlights in this issue of upstream activities:

- Rong Bao provided LAMCAS instruction set probing and feature exposure support to the Linux kernel
- Xi Ruoyao submitted a patch to fix GCC 16 generating incorrect code when compiling certain logical AND operations (`&&`)
- LXC Image Server is now shipping LoongArch template images

## Special: LXC Image Server Now Shipping LoongArch Templates

![LoongArch Templates for Linux Containers](/en/images/news/upstream/lxc-loong64.en.png)

This week, Linux Containers (LXC) started shipping official LoongArch container templates on their [Image Server](https://images.linuxcontainers.org/), making LoongArch the 5th officially supported architecture following x86-64, AArch64, AArch32 (ARMv7), and RISC-V.

LXC is a popular Linux container solution. Its operating system level containerization environment makes it easy to develop and deploy applications in different environments. LXC is also used in Proxmox VE to provide container support, allowing platforms without virtualization support, such as 2K3000/3B6000M, to deploy and manage containers.

LXC's Image Server hosts LoongArch container templates for the following distributions:

- Alpine Linux
- ALT Linux
- Arch Linux (based on [Arch Linux for Loong64](https://loongarchlinux.lcpu.dev/))
- Debian (Debian 13 based on [Loong13](https://loong13.debian.net/))
- Gentoo Linux
- openEuler

This week's activities in the Linux kernel focus on fixes for existing patches and some kernel functionalities such as BPF unit tests. The `LAMCAS` instruction support patch submitted by Rong Bao is one of the few patches to add new platform features this week.

### Platform Support

Rong Bao [submitted](https://lore.kernel.org/loongarch/20260906080316.3774-1-rong.bao@csmantle.top/) a patch to expose `LAMCAS` instruction support (part of the LA64v1.1 ISA) via `cpuinfo` and `hwcap`. The patch is now in its second revision and pending further review.

George Guo [submitted](https://lore.kernel.org/loongarch/20260904100852.26006-1-dongtai.guo@linux.dev/) the fifth revision of the LoongArch Kernel Hand-Over (KHO) support patchset, which is one of the prerequisites for the kernel live patching support, also known as Live Update (LUO). Subsequently, both Mike Rapoport and Baoquan He provided review comments, mainly focusing on the patchset's commit messages, including rewriting the "blind and unreadable" descriptions, adding AI attribution, and further wording refinements.

Qunqin Zhao [submitted](https://lore.kernel.org/loongarch/20260907023827.14905-1-zhaoqunqin@163.com/) the sixth revision of the patchset that fixes multi-node support for the Loongson Security Engine (SE), adding further code cleanups.

### KVM Subsystem

Bibo Mao [refactored](https://lore.kernel.org/loongarch/20260831094716.4016652-1-maobibo@loongson.cn/) the previously submitted patchset for independent VMID support to the third revision, continuing to refine the code and reorganize patches based on feedback from maintainers and AI review.

### BPF Subsystem

Last week, Tiezhu Yang [submitted](https://lore.kernel.org/loongarch/20260831023106.3279-1-yangtiezhu@loongson.cn/) a fix for an off-by-one error in the branch offset calculation logic of the `insn_is_cast_user()` function. This week, Tiezhu Yang submitted [the second revision of the patch](https://lore.kernel.org/loongarch/20260831023106.3279-1-yangtiezhu@loongson.cn/) refining the commit message. The patch has been merged.

Tiezhu Yang [submitted](https://lore.kernel.org/loongarch/20260902005106.22187-1-yangtiezhu@loongson.cn/) a fix for a CPU soft lockup issue triggered by the `timer_lockup` test. Tiezhu Yang noted that LoongArch is a weak memory ordering architecture, and the combination of relaxed `atomic_inc()` + `smp_mb__after_atomic()` in the current implementation is insufficient to guarantee the ordering of store and load operations (the latter is not compiled into a hardware data barrier in the current compiler implementation), which contradicts the `bpf_timer_cancel()` function documentation that explicitly states "Need full barrier after relaxed atomic_inc".

### Other Code Cleanups and Fixes

Nathan Chancellor [disabled](https://lore.kernel.org/loongarch/20260903-loongarch-disable-rust-with-kasan-v1-1-1813d3c4baad@kernel.org/) the option to enable Rust modules while KASAN (Kernel Address SANitizer) is enabled on LoongArch. Nathan Chancellor indicated that this is because the LoongArch Rust target does not support the KASAN feature, and the same applies to 32-bit ARM, for which he previously disabled the relevant support as well.

Hemanth Salem [fixed](https://lore.kernel.org/loongarch/20260904110807.19508-1-hemanth.selam@gmail.com/) a typo in a comment in `arch/loongarch/kernel/vmlinux.lds.S`.

### Binutils

Meng Qinggang [merged](https://sourceware.org/cgit/binutils-gdb/log/?qt=committer&q=mengqinggang&id=dce18441) the previously mentioned fix for expressions involving subtraction of symbol addresses and the fix to avoid using `DW_LNS_fixed_advance_pc` in debug information into the assembler (as), and merged the previously mentioned new feature written by Zhao Zhou for objdump that adds human-readable comments when disassembling `dbar` instructions.

Xi Ruoyao [updated](https://sourceware.org/pipermail/binutils/2026-August/151123.html) the patch that fixes the linker's (ld) incorrect resolution of relocations such as `R_LARCH_GOT_PC_LO12` pointing to GNU indirect functions in static linking to the second revision. Meng Qinggang noted a typo in the commit message that needs to be corrected, though the review feedback did not appear on the mailing list due to network issues.

mintsuki [proposed](https://sourceware.org/pipermail/binutils/2026-September/151202.html) adding `-shared` and `-pie` support for bare-metal targets on platforms such as LoongArch to the linker (ld). However, upstream maintainer Jan Beulich raised objections, and the discussion is still ongoing.

### GCC

<!-- https://gcc.gnu.org/git/?p=gcc.git -->

Pluto Yang [reported](https://github.com/loongson-community/discussions/issues/128) GCC 16 generating incorrect code when compiling certain logical AND operations (`&&`). Xi Ruoyao subsequently [submitted](https://gcc.gnu.org/pipermail/gcc-patches/2026-September/729526.html) a fix. The patch has not yet received review feedback, but the issue is known to affect software packages such as Qt 5 in a potentially subtle way. Therefore, **distribution maintainers using GCC 16 to build packages are advised to review and consider applying this patch**. Earlier GCC versions are not affected.

### LLVM

<!-- lrzlin 审阅；https://github.com/llvm/llvm-project -->

> This section is contributed by lrzlin, a LoongArch support maintainer for LLVM

Rui Wang [enabled](https://github.com/llvm/llvm-project/pull/220902) Post-RA (Post-Register Allocation) scheduler for the LoongArch backend, although the scheduler cannot use instruction latency information for fine-grained scheduling due to the current lack of a scheduling model. He presented dynamic instruction count and cycle data from the Clang bootstrap benchmark with Post-RA scheduling disabled and enabled, both showing improvements after enabling Post-RA scheduling.

Yongqiang Tian [discovered](https://github.com/llvm/llvm-project/issues/221109) that enabling debug information with `-g` on RISC-V and LoongArch prevents the merge-base-offset optimization from folding symbol offsets into memory access instructions, generating redundant address calculation instructions. He then [fixed](https://github.com/llvm/llvm-project/pull/221117) the issue by modifying the iterator in the relevant optimization pass to ignore debug instructions.

### LAT (LoongArch Architecture Translator)

<!-- https://github.com/lat-opensource/lat -->

> This section is contributed by "baibaidashixiong", an LAT maintainer

#### Changes Merged This Week

Wenqiang Wei (ganjue66da) [submitted](https://github.com/lat-opensource/lat/pull/427) 14 fixes and optimizations for helper functions in SoftFPU = 2 mode: explicitly closing an open helper region at translation-block boundaries, classifying x87/AVX helpers, restoring EFLAGS and high GPRs, and avoiding duplicate state saves in the inline x87 fast path.

liuchaoyi (rmjskhy) [fixed](https://github.com/lat-opensource/lat/pull/406) the LoongArch dual-instruction mixed jump that may occur when lazy-linked TB jumps are concurrently invalidated, and [fixed](https://github.com/lat-opensource/lat/pull/429) LEA incorrectly adding FS/GS segment bases.

zqz (baibaidashixiong) [added](https://github.com/lat-opensource/lat/pull/458) Steam Runtime support to LAT, dynamically discovering and isolating the pressure-vessel Runtime to prevent normal programs' `LD_LIBRARY_PATH` from mistakenly triggering Runtime library resolution; and [made](https://github.com/lat-opensource/lat/pull/441) the Steam i386 launcher report `x86_64` to select the executable x86_64 webhelper.

#### Changes Added This Week

Hanlu Li (LaurenIsACoder) continues to update the experimental [AOT static layout draft](https://github.com/lat-opensource/lat/pull/435): it inserts a small number of padding instructions only at a few safe locations in the AOT-generated LoongArch code, so that frequently executed code sequences land in different parts of the L1 instruction cache to reduce cache conflicts. The feature is disabled by default, test results vary by program, and it has not been merged.

Lu Zeng (luzeng87) [submitted](https://github.com/lat-opensource/lat/pull/440) F16C and LZCNT feature exposure: LATX can already translate half-precision floating-point conversions and count-leading-zero instructions; this PR merely reports these capabilities to x86 programs so they can select the corresponding accelerated paths. It still does not report F16C when AVX is not enabled. He also [submitted](https://github.com/lat-opensource/lat/pull/447) an indirect jump cache optimization that expands the x86_64 jump target cache and adds a secondary cache, reducing lookup overhead when translating code for indirect jumps such as function pointers and virtual calls. Stale cache entries are removed synchronously when TBs are invalidated or fully flushed.

yuerengan (y347812075) [submitted](https://github.com/lat-opensource/lat/pull/443) configurable Jcc instruction pattern optimizations, merging certain calculation instructions with subsequent conditional jumps when proven safe for EFLAGS and exception semantics; new patterns are disabled by default. He also [submitted](https://github.com/lat-opensource/lat/pull/460) optimizations that merge consecutive PUSH/POP stack pointer updates and share helper stubs to reduce repeated stack adjustments and redundant prologue/epilogue generation, with the mode stored in AOT cache headers to avoid mismatches. He also [submitted](https://github.com/lat-opensource/lat/pull/463) procfs helper-thread handling that correctly resolves relative paths, `AT_FDCWD`, and `AT_EMPTY_PATH` accesses even after a sandbox chroot, continuing to hide LATX's own helper threads from the guest program.

Xiaobai Wu (wojiushixiaobai) [submitted](https://github.com/lat-opensource/lat/pull/461) an i386 private futex fix: when LATX temporarily relocates a host page and causes a valid futex address to briefly return `EFAULT`, it returns `EAGAIN` instead as long as the guest page remains valid and readable, allowing userspace to reload and retry; truly invalid addresses still return `EFAULT`.

Wenqiang Wei (ganjue66da) [submitted](https://github.com/lat-opensource/lat/pull/464) a fix for x87 rounding synchronization: after restoring the x87 environment via `FLDENV`, `FRSTOR`, `FXRSTOR`, etc., it synchronizes the LoongArch FCSR so that translated floating-point instructions follow the guest's chosen rounding mode.

### Ports, Optimizations, and Fixes

>
> - Rong Bao (csmantle), a SpiderMonkey LoongArch JIT contributor

Rong Bao (csmantle) provided several improvements and fixes for the LoongArch backend of the SpiderMonkey JavaScript engine:

- [Fixed](https://bugzilla.mozilla.org/show_bug.cgi?id=2067330) a transient issue when operating the stack pointer, preparing for future Gecko Profiler porting
- [Optimized](https://bugzilla.mozilla.org/show_bug.cgi?id=2067472) the overall implementation of register-to-register moves, avoiding wasted space from useless instructions
- [Optimized](https://bugzilla.mozilla.org/show_bug.cgi?id=2067473) instruction selection for base-index addressing modes in certain cases, reducing register pressure and instruction count for some string and branch operations

Yuanzhen Gan (elysia-best) [added](https://github.com/loong64/cross-tools/commit/8c8567f25c84705d47a3b645e86fb03019aee9a1) the version baseline defined in the GB/T 25656 standard ("Chinese Linux Application Programming Interface (API)", commonly known as the "Linux 6.6 baseline" or "MIIT baseline") to the downstream maintained cross-tools repository by the loong64 community.

Charlie Marsh [submitted](https://github.com/astral-sh/uv/pull/21313) support for the `--python-platform` option for IBM S390x, little-endian Power (ppc64le), and LoongArch to the uv project, a Python package and environment management tool.

OBarronCS [fixed](https://github.com/pwndbg/pwndbg/pull/4104) two LoongArch platform issues in pwndbg, a debugger plugin: adding the `ret` instruction to the jump instruction classification to fix jump following, and fixing the target address calculation for `jirl`.

qiangxuhui [submitted](https://github.com/aquasecurity/trivy/pull/11159) a patch to add LoongArch binary release support to trivy, a software supply chain (SBOM) and vulnerability scanner. The upstream noted that there had been [previous discussion](https://github.com/aquasecurity/trivy/discussions/9533) on this matter, and that CI resources are limited, requiring additional support.

Samuel (Samueru-sama) [added](https://github.com/QaidVoid/zenity-rs/pull/50) binary release support for non-x86 architectures including LoongArch to zenity-rs, a simple graphical prompt tool implemented in Rust.

Vladislav Shchapov (phprus) [submitted](https://github.com/zlib-ng/zlib-ng/pull/2429) a patch to use the HWCAP facility (`getauxval`) instead of CPUCFG for probing LoongArch SIMD support in the zlib-ng project, in order to fix an illegal instruction error (SIGILL) caused by an extension supported by hardware but not kernel.

Wu Xiaobai (wojiushixiaobai) [added](https://github.com/loong64/tensorflow/commit/3f8a5bc4f51a2a7c8f52a812f48e8836deec8d51) LoongArch support to TensorFlow, an open-source machine learning framework maintained downstream by the loong64 community.

Wu Xiaobai (wojiushixiaobai) [added](https://github.com/loong64/immich/commit/e1d0bc4d64428a77f58d114f2bbb3fc80cc69407) LoongArch build support to Immich, an open-source photo management tool maintained downstream by the loong64 community.

xiaoxiaoafeifei [submitted](https://github.com/JuliaLang/julia/pull/62977) a LoongArch support patch for Julia, pending upstream review. Upstream maintainer Mosè Giordano expressed a welcome, but also indicated concerns about the long-term maintenance of this port given the current lack of LoongArch CI and limited knowledge of LoongArch among core developers.

Na Zhang (loongson-zn) [fixed](https://github.com/go-delve/delve/pull/4441) the `range-over-func` test failure on LoongArch in delve, a Go debugger.

### Dart and Flutter Port (Unofficial and Upstreaming Project)

The [Flutter-Dart-loong64](https://github.com/Flutter-Dart-loong64) and [dart-loong64](https://github.com/dart-loong64) organizations have both ported and are maintaining the Dart SDK and its related code (with different focuses between the two organizations). Developers and enthusiasts interested in the Flutter framework may visit and explore their work.

Meanwhile, Xi Ruoyao is working on a new Dart port, with the goal of reaching a quality standard that would allow submitting a pull request to the upstream, and to keep it maintainable even if upstream rejects it. For quality control and to gain experience for future maintenance, he will not use LLMs or refer to existing code from the aforementioned organizations. The port is still in its early stages, so the repository is not yet public.
