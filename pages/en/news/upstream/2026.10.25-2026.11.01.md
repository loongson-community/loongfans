## The Loongson Hobbyists' Community Website Launches the Documentation Section: The Unofficial "Volume II" is Now Available

The Loongson Hobbyists' Community website launched the documentation section last week. The long-waited unofficial LoongArch reference manual "Volume II", [*LoongArch Reference Manual Volume II-a: Vector Instruction Extensions*](https://file.loongfans.cn/loonginfo/LoongArchReferenceManual-VolumeII%28VectorInstructionExtensions%29V1.11.pdf) V1.11, is now available for download!

![The newly launched "Documentation" section](/en/images/news/upstream/20261101-community-portal-documents-index.png)

The LoongArch Reference Manual is divided into volumes by topic, of which the second volume defines vector instruction extensions. The "Volume II" released this time totals 197 pages and fully defines two SIMD vector extensions of LoongArch:

- **LSX (Loongson SIMD Extension):** an 128-bit vector extension, providing 32 128-bit vector registers
- **LASX (Loongson Advanced SIMD Extension):** a 256-bit vector extension, providing 32 256-bit extended vector registers, which is a superset of LSX, so implementing LASX necessarily means implementing LSX.

The manual covers **the complete definition of the vector instruction programming model and 8 major instruction categories (integer arithmetics, bitwise operations, string processing, floating-point operations, floating-point conversions, comparisons and selections, shuffles and mixes, and memory access)**, as well as the pseudocode semantic definitions and the instruction code encoding table for all instructions in the appendices. The V1.11 version also adds approximate reciprocal and approximate reciprocal square root instructions (`VFRECIPE`/`VFRSQRTE` and the corresponding 256-bit XV versions).

![The unofficial "Volume II" covers the vector instruction programming model and complete definitions of 8 major instruction categories](/images/news/upstream/20261101-community-portal-volume-ii-index.png)

> Editor's note: Please note that this document was obtained, organized, and hosted by the Loongson Hobbyists' Community in advance for study and research. Please refer to the official document as it becomes available.

We welcome everyone to report issues or provide suggestions during reading through community chat groups or the [issue tracker of the website source code repository](https://github.com/loongson-community/loongfans/issues). We will continue to follow up with revisions and update the version information in the documentation section accordingly.

## Correction to the Last Issue's Report on Binutils

The last issue's report on Binutils mentions:

> Zhao Zhou [removed the assembler's (GNU as) "support" for the non-existent `xvhseli.d` instruction](https://sourceware.org/cgit/binutils-gdb/commit/?id=214080ae5328425c3395a116e45d3e4c26f29515), though the editorial team is not entirely sure why logic for assembling a non-existent instruction existed in the first place.

However, Jiajie Chen's *Unofficial LoongArch Intrinsics Guide* [documented this instruction](https://jia.je/unofficial-loongarch-intrinsics-guide/lasx/undocumented/#__m256i-__lasx_xvhseli_d-__m256i-a-imm0_31-imm), and the editorial team tested it and found that it exists at least on LA664. In addition, the unofficial "Volume II" manual mentioned above also provided the encoding for this instruction (but did not describe its behavior).

Given that the functionality of this instruction (as described by Jiajie Chen) can be fully replaced by the `xvpermi.d` instruction, and that the email address shows that Zhao Zhou is an official Loongson developer, we believe that it is still best to avoid using this instruction.

## The Mainline U-Boot Successfully Boots on "Forever Pi"

<!-- 英文版可以提及 Telegram 群并加链接，中文版避嫌 -->

Recently, community contributor Yao Zi posted a screenshot of the mainline U-Boot booting on a CTCISZ Forever Pi development board based on Loongson 2K0300 in [the community chat group on Telegram](https://t.me/loongson_users).

![image](/images/news/upstream/20261101-u-boot-mainline-on-2k0300.jpg)

According to Yao Zi, booting U-Boot on real Loongson 2K0300 hardware mainly involves three parts: the mainline U-Boot port, the Tertiary Program Loader (TPL), and platform support. For the mainline U-Boot port, Yao Zi has submitted initial LoongArch support, the patch [has been revised to the 6th revision](https://lists.u-boot-project.org/pipermail/u-boot/2026-October/637826.html).

Regarding the TPL, Yao Zi explained:

> (Regarding the TPL) github.com/ziyao233/xueziloader currently handles the memory training part, with the platform initialization content here. The reasons for separating it out are, first, that LoongArch U-Boot does not yet have SPL support, and secondly, the licensing issue with the DDR firmware. The current approach requires manually specifying a copy of `libmem_config_new_abi.a` at build time to generate the firmware.
>
> Editor's note: Capitalization of some proper nouns has been modified.

Yao Zi has not yet submitted the platform support upstream and currently maintains it temporarily in [her personal repository](https://github.com/ziyao233/u-boot/tree/2k0300/demo-wip). Build with the `ctcisz-foreverpi_defconfig` configuration, combine and flash `xuezi.bin` and `u-boot-dtb.bin` to use it.

> Editor's note: As unaligned access emulation has not yet been implemented, this version of U-Boot cannot currently boot GRUB.

## Linux Kernel: Changes for Linux 7.4

![PR from Huacai Chen for Linux 7.4](/images/news/upstream/20261101-linux-kernel-7.4-pull.png)

Prior to Linux 7.4-rc1's release this week, Huacai Chen published the list of major changes for LoongArch happened during this period. Changes worth mentioning include [LoongArch ACPI IOVT support and IOMMU initialization routines](https://lore.kernel.org/loongarch/20260922121058.972734-1-maobibo@loongson.cn/) from Bibo Mao, [LAMCAS (Atomic Compare and Exchange from LoongArch) detection and reporting support](https://lore.kernel.org/loongarch/20260906080316.3774-1-rong.bao@csmantle.top/) from Rong Bao, and [various fixes and optimizations for eBPF] from Tiezhu Yang.

Apart from the PR submitted by Huacai Chen, there are some other changes that made it into this release - [the DVFS fixes](https://lore.kernel.org/loongarch/20260828031201.1500767-1-chenhuacai@loongson.cn/) mentioned in the earlier issue, and [clock property and parsing support for I²C](https://lore.kernel.org/loongarch/20260817090721.30582-1-wanghongliang@loongson.cn/). While the former can enable full DVFS support on single and multiple socket systems, when paired with 202605 and 202608 release of the UEFI firmware from our community, the latter can fix jittery/unresponsive trackpads on certain 3B6000M laptops.

At the same time, the kernel maintainers are on their way of submitting their next patchset for Linux 7.5. Stay tuned for the next report!

## Unearthing an Old News: non-x86 and AArch64 SIMD optmizations for SVT-AV1

> Editor's note: The reason why this is an "old news" is that one of our editors once thought the PR happened in last week, while in reality, this proposal integrating Highway into SVT-AVI to achieve SIMD acceleration was posted in August. It resurfaced into the PR list just because the proposal got reposted during SVT-AV1 project's migration to GitHub.
>
> But anyways, let's talk about this (again).

Those who scrolling for videos may know something called **video codec**. For a MP4 video file, common codecs include H.264 (AVC), H.265 (HEVC) and AV1.

But what, you may ask, is AV1? Like H.264 and H.265, it is a method to convert videos into a certain format (encode) to be played back (decode) later. But unlike the other two, AV1 focuses on the bandwidth efficiency, that is, to achieve highest image quality with less bandwidth usage. Therefore, video hosting platform has been migrating their video processing pipeline to AV1 since a few years ago.

![A video on Bilibili encoded with AV1](/images/news/upstream/20261101-bilibili-av1.png)

Such videos are usually encoded by hardware, for example, your GPU. For systems incapable of encoding AV1 video with hardware, a software encoder must be used, forcing the video encoding work to the CPU. SVT-AV1 (Scalable Video Technology for AV1) is one of the open-source AV1 encoder.

The goal of SVT-AV1 is to provide a solution to the performance and usability issues commonly found across early AV1 encoders such as `libaom`. Unfortunately AVT-AV1 only contains hand-written SIMD optimized routines for x86 and AArch64, and falls back to portable routines written in C on other architectures, which LoongArch is part of.

Early in August this year, community developer wszqkzqk [made SIMD acceleration for other architectures available to SVT-AV1](https://github.com/AOMediaCodec/SVT-AV1/issues/3470) by utilizing Highway as the middleware in the encoding routine.

> Editor's note: Highway is a library providing portable interfaces for SIMD intrinsics, written in C++.

![A test by the author showed a significant performance increase after introducing SIMD optimization via Highway](/images/news/upstream/20261101-svt-av1-3c5000l-highway-benchmark.png)

Once this implementation merged into the main branch, any architecture that is supported by Highway can utilize SIMD encoding acceleration. Fortunately, LoongArch is supported by Highway - a test by the author showed a 2.7x and 2.9x speedup with LSX and LAS, compared to pure scalar encoding routines, a truly considerable improvement.

In other words, on LoongArch systems without capable hardware (e.g. a newer generation AMD GPU), there will be a significant speedup when encoding an AV1 video.

## UCX Receives LoongArch Support (again)

Last week, Na Zhang [submitted patches for LoongArch support](https://github.com/openucx/ucx/pull/12187), with a test result on Loongson 3A5000M, to the Unified Communication X project, a HPC/cluster networking library. The upstream has approved and is currently awaiting CLA signage from Na Zhang.

We noticed that this is not the first time UCX has been receiving LoongArch support - earlier in May 2024, Dandan336 has submitted similar patches. However, the patches weren't merged due to lack of update and communication with upstream maintainers and other community developers.

Currently, it looks like Na Zhang has been actively responding to the reviews from upstream maintainers and the AI reviewer, keep updating their patches. Hopefully, this series of patches will be merged soon, so the people interested in HPC and distributed computing can utilize this project on LoongArch based projects.

## GoFrame Merges LoongArch Build Fixes

GoFrame is a popular Go programming framework for developing business/mission-driven systems and various types of programs. Recently, Jack Ling [submitted a fix](https://github.com/gogf/gf/pull/4950), allowing this framework to be built for LoongArch.

Developers familiar with GoFrame may want to give it a try on LoongArch.
