This article outlines LoongArch upstream activities in the past few weeks (up to UTC+8 18:00, November 15th, 2026), including ports, optimization, platform support, bug fixes and reports, etc. in Linux kernel, compiler toolchains, emulators, and other projects.

Highlights in this issue:

- Investigation: simdjson and a peculiar case of LASX performance
- GCC 17 receives multiple LoongArch optimization patches before stage 1 freezing
- Python/PyPI LoongArch support discussion receives new comments and questions
- Community developer submits a request for official LLVM APT repository support

## Investigation: simdjson and a Peculiar Case with LASX Performance

Professor Daniel Lemire from the Université du Québec à Montréal recently reported that [LASX performs worse than LSX](https://github.com/simdjson/simdjson/issues/3059) in the SIMD-accelerated JSON parsing library simdjson maintained by him: when compiled with Clang 21, enabling LASX causes the overall parsing performance to drop by about 6.7% relative to LSX only. The drop was about 3-18% when compiled with GCC 15.

He then submitted a patch to [disable LASX acceleration by default](https://github.com/simdjson/simdjson/pull/3058).

> Editor's note: LSX (Loongson SIMD eXtension) is the 128-bit vector instruction set extension on LoongArch. LASX (Loongson Advanced SIMD eXtension), on the other hand, is the 256-bit vector instruciton set extension on LoongArch.

![Professor Daniel Lemire, the author of simdjson](/images/news/upstream/20261115-prof-daniel-lemire.png)

Normally, we can achieve better performance (data throughput) using LASX with wider vector operations, the issue reported by Prof. Lemire is conterintuitive. With the question in mind, the editorial team attempted to reproduce Lemire's `dom/parse` report with GCC 16.2.0 and Clang 22.1.8, and confirmed that the issue is reproducible on both Loongson 3C5000 (based on LA464) and 3A6000 (based on LA664).

### Loongson 3C5000 (LA464, On Average)

| Compiler | LSX | LASX | Performance Improvement Relative to LSX |
| ------- | ----- | ------ | ----------------- |
| GCC 16.2.0 | 0.917405 | 0.844812 | -7.9% |
| Clang 22.1.8 | 0.919014 | 0.845466 | -8.0% |

### Loongson 3A6000 (LA664, On Average)

| Compiler | LSX | LASX | Performance Improvement Relative to LSX |
| ------- | ----- | ------ | ----------------- |
| GCC 16.2.0 | 1.935591 | 1.697195 | -12.3% |
| Clang 22.1.8 | 1.935495 | 1.696879 | -12.3% |

> Editor's note: None of the above tests specified additional optimization flags. The test script is available in this [GitHub Gist](https://gist.github.com/MingcongBai/09ddae7b69450916d85ac0764b10d323) (run directly in the simdjson source tree).

We also consulted community LLVM maintainer lrzlin regarding this peculiar case. He said that LASX register moves are more time-consuming than LSX ones, and that kind of register moves account for a high proportion of the simdjson workload, which amplifies the problem and should explain the degradation in performance as we enabled LASX. However, he also noted that there is room for optimization at the compiler level and will publish a patch soon.

## GCC 17 Development Freezing Imminent, Multiple LoongArch Optimizations Landed

GCC 17 Stage 1 is about to enter [development freeze](https://gcc.gnu.org/pipermail/gcc-patches/2026-November/737718.html), after which only fixes will be accepted. Many developers rushed to submit a large number of patches this week.

### Conditional Select/Branch Operation Optimizations

- Guo Jie [proposed](https://gcc.gnu.org/pipermail/gcc-patches/2026-November/738937.html) optimizing `(x < 0) ? x + ((1 << n)) - 1) : x` (the form which the compiler rewrites a signed integer division by the constant `1 << n` into) into `x + ((uint64_t)(x >> 63) >> (64 - n))` when `n` is a constant, avoiding unnecessary constant loads and `mask{eq,ne}z` instructions.
- Chen Xiaolong [proposed removing the negation of input conditions by inverting vector select and branch instructions](https://gcc.gnu.org/pipermail/gcc-patches/2026-November/738930.html).
- Chen Xiaolong [proposed using the `vbitsel.v` instruction to implement `((a ^ b) & m) ^ a`](https://gcc.gnu.org/pipermail/gcc-patches/2026-November/738934.html) (noting that it is an equivalent form of `(~m & a) | (m & b)`).
- Xu Jiahao [proposed reducing the cost estimate of conditional select operations](https://gcc.gnu.org/pipermail/gcc-patches/2026-November/738481.html) to encourage the compiler to use them instead of branch operations.

### Other Vector Operation Optimizations

- Chen Xiaolong proposed optimizing [vector reverse selection](https://gcc.gnu.org/pipermail/gcc-patches/2026-November/738931.html) and [same-input consecutive even/odd shuffles](https://gcc.gnu.org/pipermail/gcc-patches/2026-November/738933.html), implementing them with 1-2 LSX/LASX instructions to avoid loading index sequences from memory.
- Zhao Zhou [proposed using scalar move instructions such as `movfr2gr`, `movfrh2gr`, or `fmov` instead of vector element extraction or vector shift instructions when extracting the first (index 0) and second (index 1) 32-bit elements of a vector](https://gcc.gnu.org/pipermail/gcc-patches/2026-November/738653.html). In the follow-up discussion he [noted that at least on LA464/LA664, these scalar instructions have lower latency than vector element extraction instructions](https://gcc.gnu.org/pipermail/gcc-patches/2026-November/738707.html).
- Guo Jie [proposed using standard operation names for vector saturating subtraction instructions](https://gcc.gnu.org/pipermail/gcc-patches/2026-November/738938.html), so that architecture-independent code can use them when it recognizes saturating subtraction operations.
- Guo Jie [proposed expanding the vector element sum reduction into a chain of `vhaddw` instructions](https://gcc.gnu.org/pipermail/gcc-patches/2026-November/738939.html).

### Miscellaneous Optimizations

- Guo Jie proposed [removing the unnecessary shift-left-then-arithmetic-shift-right instructions on the source operand before `bstrins`](https://gcc.gnu.org/pipermail/gcc-patches/2026-November/738497.html).
- Xu Jiahao [proposed using the `alsl.wu` instruction to implement the operation of shifting by 1-4 bits and then zero-extending the low 32 bits of the result](https://gcc.gnu.org/pipermail/gcc-patches/2026-November/738480.html).

## Request Submitted for Official LLVM APT Repository Support

![The official LLVM APT repository currently ships packages for x86, Arm, and S390x](/images/news/upstream/20261115-llvm-apt-repository.png)

Last week, lrzlin [submitted a request to LLVM to release LoongArch binaries in its official APT repository (apt.llvm.org)](https://github.com/llvm/llvm-project/issues/240232), so that developers and users can download official toolchain binaries directly, or integrate it into their build workflows. The official LLVM APT repository provides packages for active stable branches as well as for testing branch for LLVM 24. The APT repository is operated by the [LLVM Foundation](https://foundation.llvm.org/) and is funded by third parties such as the [Open Source Security Foundation (OpenSSF)](https://openssf.org/), [Google](https://about.google/), and the [Linux Foundation](https://www.linuxfoundation.org/).

At the time of writing, the upstream have not yet responded to this request. Let's wait and see.

## Graphviz Fixes a LoongArch Bit-Width Detection Error

Several weeks ago, Vitaly Lipatov [fixed Graphviz's build tools not marking 64-bit LoongArch as a 64-bit architecture](https://gitlab.com/graphviz/graphviz/-/merge_requests/5105). Graphviz is an open-source diagram drawing and visualization tool that provides a complete set of drawing tools and bindings for multiple programming languages.

![[A diagram of the naive string matching algorithm drawn with Graphviz](/images/news/upstream/20261115-graphviz-naive-string-matching-algorithm.png)

The direct cause of this problem is that the configuration script template (`configure.ac`) of Graphviz determines 64-bit architectures using a whitelist, and LoongArch had never been added to this list, so it was always treated as a 32-bit architecture. Most of the time, this incorrect determination only affects toolchain detection and installation paths, but Vitaly Lipatov pointed out that this problem also causes the Go language bindings to erroneously use 32-bit `int` size, affecting development and runtime correctness.

> Editor's note: This patch originally came from ALT Linux and has finally been upstreamed with this merge request. We once again encourage distribution maintainers to actively submit fixes and workaround patches, so that LoongArch platform fixes, optimizations, and workarounds can spread as widely as possible.

## Follow-Up Reports

The following are several follow-up reports on previously published news items.

### Python/PyPI LoongArch Support Discussion

As of November 15, there have been some new developments in [the discussion thread started by weijie](https://discuss.python.org/t/path-towards-manylinux-pypi-support-for-loongarch64/).

Xi Ruoyao pointed out that the glibc in the Anolis 23.4 system used by the manylinux baseline contains a downstream patch with unclear purpose that lowers the minimum Linux kernel version to 4.19.0. This patch causes the `.note.ABI-tag` section of the ELF executables included in the wheel to contain the text "for GNU/Linux 4.19", making it difficult for users to distinguish whether a wheel package is released for ABI1.0 ("Old World") or ABI2.0 ("New World") systems. Xi Ruoyao suggested adjusting the manylinux build process to ensure that the glibc it uses does not carry this downstream patch.

Subsequently, Ralf Grommers, a member of the Python Packaging Council, expressed approval in principle but also raised questions such as whether the LSX baseline is sufficiently general, as well as concerns about maintenance cost and compute capacity. weijie is actively answering these questions.

### EDK II Receives LoongArch Unit Testing Support

After Chao Li's change [adding Ubuntu 24.04-based LoongArch build and runtime test support](https://github.com/tianocore/containers/pull/126) to the TianCore testing infrastructure was merged two weeks ago, Dongyan Qian (MarsDoge) [submitted LoongArch testing support](https://github.com/tianocore/edk2/pull/13482) to EDK II.

At the time of writing, the change has received approval from NetworkPkg maintainer Antaeus Kleinert-Strand and is awaiting review and comments from other maintainers.
