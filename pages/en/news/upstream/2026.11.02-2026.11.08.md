This article outlines LoongArch upstream activities in the past few weeks (up to UTC+8 18:00, November 8th, 2026), including ports, optimization, platform support, bug fixes and reports, etc. in Linux kernel, compiler toolchains, emulators, and other projects.

Highlights in this issue:

- Python/PyPI LoongArch support: upstream contributors initiate discussion on baseline definition
- LoongArch automated testing infrastructure added to FFmpeg and TianoCore
- Reverse engineering suite REA (Reverse Engineer Anything) reviewing LoongArch (Ghidra) patches

## Python/PyPI LoongArch Support Discussion Rebooted

After almost a year of silence, discussions around Python/PyPI LoongArch support and baseline definitions has seen new developments. Last week, weijie posted plans on the Python forum to [defines a manylinux/musllinux baseline](https://discuss.python.org/t/path-towards-manylinux-pypi-support-for-loongarch64/105548/5), seeking feedback from the community. The final goal of establishing this baseline is to enable binary distribution of LoongArch Python/PyPI packages, making it easier for developers and researchers using Python to install dependencies via pip and other tools.

![PyPI's list of binary distributions for Pandas, a data analytics toolkit for Python - there are currently no LoongArch binary distributions (note: for better illustration of this list, the editor removed the source distribution section from the webpage).](/images/news/upstream/20261108-pandas-3.1.1-bindist.png)

This baseline discussion is based on the [manylinux/musllinux definition merged back in June](https://github.com/pypa/manylinux/pull/1927):

- `manylinux_2_38_loongarch64`: based on Anolis 23.4 and glibc 2.38
- `musllinux_1_2_loongarch64`: based on Alpine 3.22 and musl 1.2

Among them, the glibc version chosen for the manylinux baseline (2.38) is higher than the version that first supported LoongArch (2.36), while Rust and other toolchain binaries also chose 2.36. musllinux does not have this issue.

However, the impact of this baseline difference should be insignificant - although glibc only implements backward compatibility (simply put, setting a glibc 2.38 baseline means systems using earlier glibc versions will not be able to use binaries built in this environment), current ABI 2.0 ("New World") distributions in reality almost never use a glibc version lower than 2.38.

In addition, weijie also proposed a plan to set the platform ISA/ABI baseline:

- LoongArch64 (LA64)
- Double-precision floating-point ABI (LP64D)
- ELF object ABI v1
- Requires LSX (128-bit vector extension)

Discussions on the LoongArch PyPI baseline, tags, and related topics are still ongoing, and we strongly recommend those who develops with Python follow this discussion and offer their own opinions based on their use cases.

## FFmpeg: LoongArch Automated Testing Wired Up, Enables Tree Vectorization by Default

Two weeks ago, FFmpeg [added a four-socket Loongson 3C5000 server to its FATE automated testing cluster](https://code.ffmpeg.org/FFmpeg/FFmpeg/pulls/25141) after discussions with Loongson engineers, enabling continuous testing on the LoongArch platform.

![FFmpeg's FATE cluster status page (https://fate.ffmpeg.org/) - at the time of writing, the LoongArch build machine has not yet come online.](/images/news/upstream/20261108-ffmpeg-fate.png)

> Editor's note: [FATE](https://fate.ffmpeg.org/) is the abbreviation of FFmpeg Automated Testing Environment.

Last week, upstream developer Kacper Michajłow enabled tree vectorization support by default for LoongArch build targets using GCC ≥ 14.4/15.2/16. This allows the compiler to automatically convert scalar loops or serial operations into parallel operations using SIMD technology (such as LoongArch's LSX/LASX vector extensions), achieving performance gains. The GCC version restriction is due to older GCC versions having [an issue that causes this optimization to generate incorrect code for FFmpeg](https://gcc.gnu.org/PR121064).

The degree to which this could improve FFmpeg's performance on LoongArch remains to be tested and verified.

## TianoCore Testing Infrastructure Receives LoongArch Support

![New commits and pull requests received by TianoCore will now run LoongArch build and runtime testing.](/images/news/upstream/20261108-tianocore-ci.png)

Last week, Chao Li [added LoongArch build and runtime testing support based on Ubuntu 24.04](https://github.com/tianocore/containers/pull/126) to the TianoCore testing infrastructure, enabling automated CI testing for EDK II components. Similar to FFmpeg's FATE infrastructure adopting LoongArch, such testing helps upstream developers understand the impact of various changes on systems and microarchitecture environments including LoongArch, avoiding performance, functional, or issue regressions.

## Agentic Reverse Engineering Suite REA (Reverse Engineering Anything) Receives LoongArch (Ghidra) Support

Readers may have heard of the [REA (Reverse Engineer Anything)](https://rea.tools/), a reverse engineering suite for AI agents, which has recently gained massive attention in the community. By implementing an MCP (Model Context Protocol) server, it enables AI agents to automatically invoke various reverse engineering tools, automating reverse engineering of various application and service programs.

![Ghidra running on LoongArch.](/images/news/upstream/20261108-ghidra-on-loongarch.png)

One of the tools REA uses is Ghidra, and last week, community developer Red54 [submitted LoongArch binary reverse engineering support based on Ghidra](https://github.com/morluto/rea/pull/9146), marking one of the first steps towards LoongArch support in REA.

The pull request is still pending review, welcome to try it out.

## The Linux Kernel: Quiet Again After the 7.4 Merge Window

After the release of Linux 7.4-rc1 last week, activities in the Linux kernel settled down somewhat this week. This week, the Linux kernel [loongarch mailing list](https://lore.kernel.org/loongarch/) received several patches for new LoongArch features and fixes.

In terms of platform support, Binbin Zhou submitted the initial patchsets for the [Loongson 2K0300/2K3000 UART driver](https://lore.kernel.org/loongarch/cover.1793776192.git.zhoubinbin@loongson.cn/) and [a series of SPI driver fixes](https://lore.kernel.org/loongarch/cover.1793689461.git.zhoubinbin@loongson.cn/). The latter fixes functions including SPI mode selection caching, chip-select initial value selection, runtime probing of power management register state, and clock divider calculation. Huacai Chen has reviewed and approved both patchsets.

In the BPF subsystem, Tiezhu Yang [corrected](https://lore.kernel.org/loongarch/20261102072808.23080-1-yangtiezhu@loongson.cn/) the BPF Arena support baseline to require the SC.Q instruction, and used beqz/bnez instructions to avoid potential branch overflow issues. Huacai Chen and George Guo provided revision suggestions, and Tiezhu Yang said he will submit the revised patchset this week.

> Editor's note: The SC.Q instruction was introduced with the LoongArch ISA v1.1 and is used to implement conditional stores of 128-bit data. Currently, LoongArch processors based on the LA364E and LA664 cores are known to implement this instruction set, namely the 2K3000/3B6000M and 3A/B/C6000 series processors.

Over the past week, the loongarch mailing list also received a series of fixes from Jinjie Ruan and Mike Rapoport covering areas such as kexec and memory management:

- **Jinjie Ruan:** Fixed a reference leak of modified_cmdline in the LoongArch kexec code ([1st revision](https://lore.kernel.org/loongarch/20261105130113.2284690-1-ruanjinjie@huawei.com/))
- **Jinjie Ruan:** Fixed a reference leak of `elf_headers` in the LoongArch kexec code ([1st revision](https://lore.kernel.org/loongarch/20261105130113.2284690-1-ruanjinjie@huawei.com/))
- **Mike Rapoport:** Used DMW (Direct-Mapped Window) to restore KFENCE memory pages on hibernation (ACPI S4) resume, avoiding kernel `BUG()` reports such as use-after-free during the resume process ([1st revision](https://lore.kernel.org/loongarch/20261031-fixes-loongarch-v1-1-e0e33e3c008e@kernel.org/))

Huacai Chen has merged all three fixes above at the time of writing.

## GNU Toolchain

### GCC Performance Optimizations

Deng Jianbo [submitted a patch to remove the `*` modifier on floating-point register constraints in the `movdi_64bit` pattern](https://gcc.gnu.org/pipermail/gcc-patches/2026-November/737572.html) (which, when generating assembly code, prints as the `move` pseudo-instruction or instructions such as `fmov.d`, `movgr2fr.d`, `ld.d`, and `fld.d` depending on the actual locations of the source and destination). This modifier was originally added to prevent the compiler from unnecessarily placing integer values into floating-point registers, but it has now been found that such problems do not seem to occur without the modifier, and the modifier also causes the compiler to unnecessarily split `fld.d` instructions into `ld.d` and `movgr2fr.d` instructions.

Deng Jianbo's own SPEC CPU 2017 test results show that removing the modifier can achieve considerable performance improvements in some floating-point subtests, but those results were obtained under `-Ofast -mlasx`, and the effect on actual software package builds (which usually do not use `-mlasx` and almost certainly do not use `-Ofast`) remains to be verified.

In addition, Deng Jianbo [submitted a patch that fixes the missing data dependency issue in the inline assembly](https://sourceware.org/pipermail/libc-alpha/2026-November/181881.html) for glibc's tst-gnu-tls2 test. However, this test did not fail previously, we speculate that the above GCC optimization may have exposed this issue.

### Miscellaneous BFD Linker Fixes

Zhao Zhou submitted several patches to fix logic errors or sometimes even crashes in the BFD linker when handling several illegal inputs such as [passing in non-LoongArch binaries](https://sourceware.org/pipermail/binutils/2026-October/152280.html), [using relocations that require GOT/PLT entries in non-ALLOC sections](https://sourceware.org/pipermail/binutils/2026-October/152280.html), and [containing unresolvable relocations that trigger debug output printing all relocations](https://sourceware.org/pipermail/binutils/2026-October/152261.html).

In addition, he [submitted a patch fixing a linker crash when an input relocatable object file (`.o`) contains `R_LARCH_TLS_{LD,GD,DESC}_PCREL20_S2` relocations](https://sourceware.org/pipermail/binutils/2026-November/152440.html). Due to LoongArch code model limitations, actual `.o` files generally do not encode them directly. Instead, they encode `R_LARCH_TLS_{LD_GD_DESC}_PC_{HI20,LO12}`, which the linker relaxation then converts to `R_LARCH_TLS_{LD,GD,DESC}_PCREL20_S2`, so this issue does not trigger in that case.
